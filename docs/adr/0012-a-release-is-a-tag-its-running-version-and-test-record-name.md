# A release of Benchline is a tag, which its running version and automated test record name

Computerised system validation must reference one frozen release (zhipengzhu1-dotcom/13-Sep-2026-SOP-Management#12), and change control after Go-live is a procedure: the Benchline change control SOP, with tiered change records and a release record the Quality lead approves before deployment (SOP-Management#10, #46). That procedure needs Benchline itself to say which release is which, what was tested and what is running. Until #61 it had no tags, no CI and a `package.json` version that never changed.

We decided that a release is a git tag naming the version in `package.json`: `vX.Y.Z-rcN` for a release candidate, `vX.Y.Z` for a final release. A tag is never moved or deleted. A candidate that fails, or needs any change, is followed by the next candidate, and the final release is tagged on the validated candidate's commit with only the version changed. Configuration changes to an instance follow the same change control, through `docs/instance-settings.md`.

On every release tag, CI runs `npm run check` on the tagged commit and keeps the log with its SHA-256, whether it passed or failed. Each run's log goes to a workflow artifact and to the tag's GitHub Release, and no rerun replaces an earlier log. A failed run leaves the tag marked as a pre-release that is not releasable. Neither copy is the record: the logs are filed in the lab's controlled validation records. They are automated test evidence that validation references, not validation itself, which remains the signed user acceptance tests on the Validation environment against the same tag (ADR-0001).

The running server prints its version and commit at start-up, and the workspace shows them, so the deployment log can record which release is live. A build that is not exactly its tag, unchanged, says `not the release`, and it must not run as the Production instance or the Validation environment. The System administrator deploys a tag only after the Quality lead approves its release record (ADR-0007). That record names the tag, the commit, the CI runs and their log checksums.

GitHub's tag rulesets need a paid plan for a private repository, so nothing technical stops a tag being moved. The release record's commit and log checksums make a moved tag or a swapped log detectable instead. If the repository gains rulesets, `v*` tags are protected against update and deletion.

We rejected keeping the test log only as a workflow artifact, because it expires after 90 days, and keeping only passing runs, because FDA's data-integrity guidance (Q13) keeps failing and suspect runs on the record too. We also rejected stamping the version without the commit, because the same version number alone does not show that the tested build is the one running. Stamping the version on each laboratory record stays a later enhancement (#46).
