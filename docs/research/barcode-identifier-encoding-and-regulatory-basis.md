# What are the established facts about encoding and scanning a laboratory identifier of the shape LAB-{year}-{6 digits}, and does any primary regulatory text bear on barcode use in a pharmaceutical QC laboratory record?

**Asked by:** Ticket on "scan to open" as the primary retrieval path (orchestrator dispatch), referencing the fixed `LAB-{year}-{6 digits}` format and the aliquot/movement-history decisions.
**Date:** 2026-09-11
**Status of sources:** eCFR text for 21 CFR Parts 11, 211, and 201 fetched live via the eCFR versioner API (point-in-time 2025-01-01, current at time of query) and grepped directly — not recalled. FDA's *Data Integrity and Compliance With Drug CGMP* guidance fetched from the canonical URL (https://www.fda.gov/media/119267/download) and confirmed as the **December 2018** final version by text inside the PDF itself (not a draft). PIC/S PI 041-1 fetched from picscheme.org (docview/4234) and confirmed as the **1 July 2021** final version by the header/footer text on every page. ISO/IEC standard texts themselves (15417, 16022, 18004) are **paywalled at iso.org**; what follows for those three is drawn from ISO's own abstract/scope pages (iso.org/standard/...) plus GS1's freely published General Specifications, and is marked as such — I did not access or paraphrase the full paywalled standard bodies.

## Findings

### 1. Symbology capacity and constraints for `LAB-2026-000417` (15 chars, uppercase A–Z, 0–9, hyphen)

- **Code 128** (ISO/IEC 15417): encodes the full 128-character ASCII set via three interleaved sub-sets, Code Set A (control + upper-case + punctuation), Code Set B (upper/lower-case + punctuation, no control), and Code Set C (pairs of digits, 2 digits per symbol character). ISO's own scope note: "specifies the requirements for the bar code symbology known as Code 128... specifies Code 128 symbology characteristics, data character encodation, dimensions, decoding algorithms" (iso.org/standard/43896.html — abstract page, standard body itself paywalled). Because `LAB-2026-000417` mixes letters, digits and a hyphen, an encoder would use Code Set B for the alpha/hyphen portions and could switch to Code Set C for the six-digit run to shrink it (2 digits per bar pattern instead of 1). *Confidence: standard's scope confirmed from ISO's own page; the Code Set A/B/C mechanics are corroborated by multiple independent technical summaries (Wikipedia, GS1, vendor barcode guides) that agree with each other and with the ISO abstract — treated as reliable secondary corroboration of a paywalled primary source, not as the primary source itself.*
- **Code 39**: historically restricted to 43 characters — upper-case A–Z, 0–9, and the symbols `- . $ / + % SPACE` — which is sufficient for this identifier's character set (upper-case, digits, hyphen), but Code 39 has no digit-pair compression and is markedly less dense per character than Code 128, so the same 15-character string produces a physically longer barcode. *Confidence: consistent across secondary sources; I did not access the ISO/IEC 16388 (Code 39) standard text itself, which is also paywalled.*
- **Data Matrix ECC 200** (ISO/IEC 16022): a 2D matrix symbology, square or rectangular, module count from 10×10 up to 144×144 (even values only) per ISO's own scope/abstract page (iso.org/standard/44230.html — again, abstract only, standard paywalled). Vendor/technical summaries converging on the same figures state maximum theoretical capacity around 3,116 numeric digits, 2,335 alphanumeric characters, or 1,556 8-bit bytes at the largest symbol size — far more than the 15 characters needed here, meaning a small module count (well under the maximum) would suffice. *Confidence: symbol size range attributable to ISO's own page; the specific capacity numbers are vendor/technical-summary figures, not verified against the paywalled standard text itself — labelled as such.*
- **QR** (ISO/IEC 18004): current edition is ISO/IEC 18004:2024 per ISO's own product page (iso.org/standard/83389.html); an earlier 2015 edition (iso.org/standard/62021.html) is also listed by ISO. Versions run 1 (21×21 modules) to 40 (177×177 modules), with four Reed–Solomon error-correction levels (L/M/Q/H). For a 15-character alphanumeric-plus-hyphen string, a low QR version (well under 40) at a low-to-medium error-correction level would be more than sufficient. *Confidence: version/module range and error-correction levels are consistent across ISO's own scope text and secondary technical summaries; exact capacity-per-version tables were not read from the paywalled standard itself.*

**Note on the identifier's own characters:** the hyphen is within Code 39's native character set and within Code 128 Code Set B, and is representable as plain ASCII data in Data Matrix and QR, so no symbology here is disqualified by the hyphen.

### 2. Minimum readable label size and print-resolution constraints

- GS1's own **freely published** General Specifications state that for GS1-128 (a Code 128 variant), quiet zone width must be a minimum of 10× the X-dimension on each side, and X-dimension must be constant throughout a symbol (ref.gs1.org/standards/genspecs/, corroborated by the GS1-128 FAQ summary). *Confidence: high — GS1's specification is itself an authoritative, freely accessible primary source for GS1-flavoured symbologies (distinct from the base ISO/IEC standards, which govern the symbology mechanics but not GS1's application rules).*
- For **GS1 DataMatrix**, GS1's own guideline states the minimum X-dimension (module size) is 0.396 mm (0.0150 in) and the maximum is 0.990 mm (0.0390 in), with quiet zone equal to one X-dimension on each side. *Confidence: high, GS1's own published guideline.*
- **Print resolution:** vendor and industry guidance (not a standards body) converges on: 203 dpi (8 dots/mm) is adequate for larger barcodes and standard labels but is documented by multiple vendor sources as producing unreliable scans on small labels (example figure cited: a 1"×0.25" label may not print a scannable barcode at 203 dpi); 300 dpi (12 dots/mm) roughly doubles dot density, allowing proportionally smaller barcodes for the same reliability. *Confidence: this entire paragraph is vendor/industry guidance, not standards text — labelled explicitly as such per the task's requirement to distinguish "the standard says" from "a vendor says."* No ISO/IEC or GS1 primary source was found specifying a minimum dpi requirement as such; the standards specify X-dimension and quiet-zone geometry, and it is print-resolution (dpi) that determines how faithfully a given X-dimension is reproduced — the translation from "X-dimension required" to "dpi required" is vendor-guidance territory, not standards territory.

### 3. Keyboard-wedge behaviour

- A USB "keyboard wedge" barcode scanner enumerates on the host as a USB HID (Human Interface Device) keyboard class device; the operating system's built-in generic keyboard driver handles it, and the scanned payload arrives at whatever application/field currently has input focus as a sequence of keystrokes, typically followed by a terminator keystroke. The most commonly configured terminator is Enter/Carriage Return (CR, 0x0D), sometimes Tab (0x09) or a CR+LF pair. *Confidence: high for the HID mechanism itself, since USB HID is a published USB-IF standard class; corroborated by multiple independent scanner vendor manuals (e.g. the Zebra/Symbol LS2208 reference guide) describing the same terminator conventions.*
- **Prefix/suffix configuration is per-vendor/per-device**, typically set by scanning a configuration barcode from the manufacturer's programming guide (e.g. Zebra's LS2208 manual). I found **no ISO/IEC or other standards-body specification** that mandates a particular prefix or suffix sequence for keyboard-wedge scanners; this appears to be vendor convention, not standardized behaviour. This is an absence and is reported as such.
- The established **browser-side technique** for distinguishing a scan from human typing, as described in general technical guidance (not a standards document), relies on one or more of: (a) measuring inter-keystroke timing, since scanners emit characters far faster than a human typist; (b) requiring a dedicated, always-focused input field for scan entry; (c) detecting a configured prefix character if the scanner is set to emit one. None of these is a documented industry or regulatory standard — they are established *practice*, described consistently across scanner-integration guides, but not codified in any primary source found.

### 4. 1D vs 2D scanner reality

- Multiple independent scanner-vendor and integrator sources agree: a 2D imager (camera-based scan engine) can decode both 1D linear symbologies (Code 128, Code 39, EAN/UPC, etc.) and 2D matrix symbologies (Data Matrix, QR, PDF417, Aztec); a 1D laser scanner can only read 1D linear symbologies and cannot decode 2D matrix codes at all. *Confidence: consistent and unremarkable across every source checked; this is standard industry knowledge, not something the ISO standards themselves assert (each ISO/IEC symbology standard specifies the symbology, not what scanner hardware can decode it) — no standards-body citation exists for this specific claim, only device documentation and integrator guides.*
- The practical implication (stated as fact, not recommendation): choosing a 2D symbology now does not foreclose 1D-only scanners already in a lab from being useless against it, since 1D hardware cannot read 2D codes; choosing a 1D symbology remains readable by both 1D and 2D scanner hardware.

**This is a genuine absence, and it is reported as a finding:** none of Part 211, Part 11, the FDA Dec-2018 data-integrity guidance, or PIC/S PI 041-1 mentions barcodes, bar codes, machine-readable identification, or scanning of identifiers anywhere in their text. PIC/S's seven "scan" hits are exclusively about (a) scanning paper records to create a "true copy" under document-control expectations, and (b) IT-security "vulnerability scans" and USB-device malware scanning — none address identity capture of a sample, container, or laboratory number.

**Part 201 scope, established directly from the section text (21 CFR 201.25):** the bar code requirement applies to "manufacturers, repackers, relabelers, and private label distributors of a human prescription drug product or an over-the-counter (OTC) drug product," requires the National Drug Code (NDC) in a linear bar code meeting EAN/UCC or HIBCC standards, and "the bar code must appear on the drug's label as defined by section 201(k) of the Federal Food, Drug, and Cosmetic Act" (§201.25(c)(2)). This is unambiguously scoped to the **finished, marketed drug product's label** — it governs what a manufacturer prints on the product a patient or hospital receives, not any record, sample, or container identifier generated inside a QC laboratory. Nothing in Part 201 reaches, extends to, or is analogized to a laboratory sample number in the text itself.

**Conclusion of this section:** no primary regulatory source examined imposes, recommends, or even discusses a barcode/scan requirement for laboratory identifiers. The only CFR text mentioning barcodes at all (Part 201) is scoped to finished-product labeling for patient/hospital distribution and does not reach laboratory records.

### 6. Transcription error rates

- The commonly circulated figures — "manual keying error rate ≈ 1 in 300 keystrokes" and "barcode scan error rate ≈ 1 in 3 million (or better) scans" — were searched specifically for a traceable origin. The search results returned only **industry blog posts, vendor marketing pages, and warehouse/logistics content** (loftware.com, hprt.com, advanced-automationinc.com, and similar), all restating the same two numbers without citing a study, standards body, or dataset. One older reference to "1/300" keyboard error appears inside a USPTO utility patent's background section (a lab-equipment patent, not a standards or peer-reviewed source), used there as a general comparison rather than a cited measurement. **No standards body (ISO, ANSI, NIST), peer-reviewed publication, or government agency source was found to be the origin of either number.** The trail ends in vendor/marketing restatement of an unsourced pair of figures that appear to circulate by mutual citation among barcode-industry marketing content, not from a traceable study.
- Consistent with prior scouting on this map's rejection of the untraceable "2.3%, WHO" figure, the same treatment applies here: **these two figures should not be cited as an authoritative error-rate comparison**, because no primary source was found underpinning them.
- No credible peer-reviewed or government-agency figure specific to pharmaceutical QC laboratory transcription vs. scanning was found in this search, consistent with the prior finding on this map that no such data exists for pharma QC specifically.
