# Is the raw-data system a second entity, and what does a suspect window scope to?

**Asked by:** ticket #55, "Is the raw-data system a second entity, and what does a suspect window scope to?"
**Date:** 2026-09-11
**Status of sources:** Vendor-hosted documentation was reached for Waters Empower (`support.waters.com`, `help.waters.com`) and Thermo Chromeleon (`documents.thermofisher.com`, `appslab.thermofisher.com` — Thermo's own AppsLab subdomain). Agilent OpenLab CDS documentation could not be reached (HTTP 403 from `agilent.com`, connection refused from a mirror) — this is a real gap, not paraphrased from secondary sources. Shimadzu LabSolutions primary documentation was not reachable within this pass; only reseller/marketing summaries turned up, which are recorded as secondary and NOT used as findings. FDA's OOS guidance (May 2022 Rev 1) was already retrieved and cited by the ticket description itself and is treated as current per that framing. USP <621> and <1058> were not attempted to be fetched directly given the known paywall (per project convention on stdlib sources) and are recorded below as an open flank rather than paraphrased.

## Findings

### 1. Record hierarchy

**Waters Empower** — verified, vendor primary (Waters support KB + Waters help site).

- The vendor's own nouns, from Waters KB and help pages: **Project → Sample Set (built from a Sample Set Method) → Injection → Result Set → Result.**
  - A "Sample Set Method" is the template Empower uses to build the run list; "Data Acquisition and the Sample Set Method" is an official Empower Tip title (help.waters.com/help/en/product-support/empower-chromatography-data-system-support/empower-tips/tip-13.html), confirming the Sample Set Method as a distinct named object from the Sample Set itself. (Retrieved 2026-09-11; page content could not be fully rendered by the fetch tool due to a timeout, so this is confirmed only at the level of the page title and surrounding search snippet, not full body text — flagged below as partially verified.)
  - Each row of a Sample Set is an **Injection**, carrying a **Function** (e.g. "Inject Standards," "Inject Samples," "Inject Controls," "Inject Immediate Standards/Samples," "Calibrate," "Report," "Equilibrate," "Condition Column," "Purge Inj," "Purge Det"). Source: Waters KB article WKB119148, "What is the meaning of each function displayed in the Function column of the Empower 3 sample set?" (support.waters.com, retrieved 2026-09-11, fetched and summarized above).
  - Processing a Sample Set produces a **Result Set**: "a bound collection of results" (per Waters KB search summary of WKB5025/WKB797/WKB15516, support.waters.com, retrieved 2026-09-11).
  - Injections can be recombined outside their original Sample Set into a **"Process Only Sample Set"** built from selected Injections or Channels, then processed to generate a new Result Set (Waters KB, "How to Create a Process Only Sample Set," support.waters.com/Tip 237, retrieved 2026-09-11). This is a documented vendor mechanism for re-grouping injections independent of the run that acquired them — i.e. the Sample Set that *acquired* data and the Sample Set (or Process Only Sample Set) that *processed* it into a Result Set need not be the same object.
  - **Which level carries a human-readable unique identifier, and which carries an acquisition timestamp**: not confirmed from documentation reachable in this pass. Empower's Sample Set and Injection both have names/vial identifiers entered by the operator, but I did not reach a page that states unambiguously which field is guaranteed unique versus which is a label. This is recorded under "could not establish" below rather than asserted.

- **System suitability scope, Waters' own language**: "System Suitability is a series of injections you can make to help you determine the suitability and effectiveness of your chromatographic system before use. System Suitability requirements must pass to guarantee the quality of the sample run results." (Waters, summary drawn from "Using Interactive System Suitability in Empower 2," help.waters.com/content/dam/waters/ko/support/technicalnotesservice/2009/TECN10115982, and the Empower Tip "System Suitability," help.waters.com/help/en/product-support/empower-chromatography-data-system-support/empower-tips/tip-317.html — both retrieved 2026-09-11.) System suitability is evaluated **over a set of injections within a Sample Set**, and Waters documents **bracketing**: "you could have an area count average of 5 system suitability injections and a total of three bracket injections, where each bracket RSD is calculated with the system suitability injections plus the respective bracket injection(s)" (Waters Forums thread, secondary/lower-confidence — a user forum, not vendor documentation; flagged as such and not relied on alone). The vendor-hosted "Elaborate sample set with bracketing" and "Rolling Bracket Recovery by Custom Field" threads on forums.waters.com corroborate that "bracket" is Empower's own UI term but these are user forum posts, not documentation — secondary.
  - **Interactive System Suitability fault handling**, Waters' own language (from the Empower Tip "Using Interactive System Suitability," retrieved 2026-09-11): a suitability fault triggers the **Suitability Mode** selected when the sample set was started — "Stop on fault" halts acquisition immediately; "Reinject on fault" reinjects the suitability samples per the Label Reference column. This locates the suitability judgement's *consequence* at the level of the running Sample Set (it can stop or continue the whole run), not at a single injection in isolation, though the fault condition itself is computed from a specific subset of injections (the suitability/bracket injections).
  - I did **not** find, in vendor documentation reached this pass, an explicit statement of a "suspect"/"voided"/"not-for-reporting" injection status in Empower. The Function-column list from WKB119148 does not include such a state; it lists acquisition/processing/instrument-maintenance functions only. This is recorded as an open question below, not as a negative finding, since I did not reach Empower's System Suitability Quick Reference Guide (715007659, waters.com) — the fetch timed out — nor an administrator/compliance guide that might document a "not for reporting" or exclusion flag on a result or injection.

**Thermo Chromeleon** — verified, vendor primary (Thermo-hosted PDF brochure and AppsLab eWorkflow guide, both fetched and text-extracted directly, retrieved 2026-09-11).

- Vendor's own nouns, top to bottom: **eWorkflow (a template/procedure) → Sequence → Injection.** Quoting the Thermo brochure ("eWorkflow Procedures," documents.thermofisher.com/TFS-Assets/CMD/brochures/SP-70758-CDS-Chromeleon-Streamline-Workflow-SP70758-EN.pdf): "A sequence is the basic unit of data in Chromeleon comprising a set of injections that belong together and contains all data and meta-data necessary to recreate sample analysis results" (paraphrase of vendor search-summary language; the PDF's own body text states an eWorkflow procedure "captures all the unique aspects of [a] ... workflow" and "simplifies correct sequence" creation).
  - The **Sequence** is named automatically: "the name of the sequence is composed of the eWorkflow name and a date-time [stamp]" (AppsLab eWorkflow guide, appslab.thermofisher.com/Content/GettingStarted/AppsLab%20Library%20-%20eWorkflow%20-%20English.pdf, §3.3, "Running the Sequence," retrieved and text-extracted 2026-09-11). This is the clearest documented case of a container-level identifier that embeds an acquisition-adjacent timestamp — the Sequence name itself, not the individual injection.
  - A **"Default Channel"** setting exists at the Sequence-General level, described as depending "on the instrument and corresponding [detector/channel configuration]" (same guide, Table 4/Table 7, "Default Sequence General settings"). This documents "channel" as the vendor's noun for a detector/data-stream within an instrument, distinct from "instrument" itself.
  - **Bracket, Chromeleon's own definition, quoted verbatim** (AppsLab eWorkflow guide, §4.3/§5.3, "Sequence Layout"): "**Bracket** — Injections that will be performed between sample blocks (for example, calibration standards). A bracket separates two sample blocks from each other." The same section defines **Sequence Header** ("Injections that always appear at the beginning of a sequence, such as blank injections") and **Sequence Footer** ("Injections that always appear at the end of a sequence") as the other two structural block types, alongside the **Sample** block itself. This is a load-bearing, verbatim vendor definition: a Chromeleon "bracket" is an **injection-level grouping construct that sits between two sample blocks**, not a property of the whole sequence and not a single injection.
  - Chromeleon documents **linked instruments**: "You can create a sequence using either one or both linked instruments... the eWorkflow Wizard shows the instrument name as part of the sequence preview" (Thermo brochure, retrieved 2026-09-11). This confirms a Sequence can span more than one physical instrument, and that "instrument" (named) is the vendor's noun for the addressable apparatus at this level of the documentation, distinct from "Instrument Controller" (see §2 below).
  - I did **not** reach documentation in this pass that names an explicit "voided"/"suspect"/"not for reporting" injection state, or that states unambiguously where the audit trail lives (Sequence-level vs. injection-level) beyond the brochure's mention of a "**Sequence Data Audit Trail**" (quoted directly from the brochure text, §"eWorkflow procedures can also..."). That phrase — "Sequence Data Audit Trail" — is the one piece of vendor terminology found that locates the audit trail nominally at the Sequence, not the injection, but I did not reach a page describing its contents or scope in detail, so this is a partial finding.

### 2. Acquiring apparatus: software instance vs. physical instrument

- **Chromeleon** distinguishes **"Instrument Controller"** from the sequence/injection layer. The Thermo brochure text found in this pass states only that issues with data acquisition require stopping/restarting "the Instrument Controller" to regain instrument access (this specific sentence came from a search-engine summary of a different Thermo page, not from the two documents I fetched and text-extracted — flagged as **secondary/unconfirmed** within this pass, since I did not independently verify it in the fetched brochure or AppsLab guide text, and a grep of both extracted texts for "Instrument Controller Service" returned no hits). What **is** confirmed directly from the fetched, text-extracted documents: Chromeleon supports **"linked instruments"** — two named instruments that a single sequence can span (brochure text, quoted above) — which is itself evidence that one Sequence-creation action can address more than one physical instrument by name, and that "instrument" is a named, addressable object distinct from the sequence.
- I did **not** find, in the documents reached this pass, any statement about whether a Chromeleon "instrument" object carries an identity independent of the lab's own asset tag, or whether an instrument can be re-registered / moved between Chromeleon servers. This is an open question, not a negative finding — I did not reach Chromeleon's administration or instrument-configuration documentation.
- **Empower**: no documentation reached in this pass addressed instrument naming, multi-instrument-per-node topology, or instrument re-registration between Empower servers. Open question.
- **OpenLab / Shimadzu**: unreached; open question for both, compounded by the outright inability to reach vendor documentation at all (see §1).

### 3. Invalidation / exclusion mechanisms

- **Empower**: the Function-column list from Waters KB WKB119148 includes **"Summarize Custom Fields (Exclude Faulted)"** — described in the search-summary as performing "a similar calculation while excluding abnormal results." This is the one documented Empower mechanism found this pass that names an *exclusion* concept, and it operates at the level of **custom-field summarization across faulted results within a sample set**, not an explicit per-injection "void" or "not for reporting" state. I did not find a "not for reporting" checkbox, flag, or state documented in the sources reached.
- **Chromeleon**: no exclusion/voiding mechanism was found in the two documents fetched and text-extracted this pass. Not established either way.
- Neither OpenLab nor Shimadzu documentation was reached, so nothing can be reported for either on this question.

### 4. "Raw data" / "original record" statements

- No vendor statement defining "raw data," "complete data," or "original record" was found in any of the documents reached this pass, for any of the four vendors. This is a **full gap** across the board, not a per-vendor finding — none of the fetched pages (Waters KB articles, Waters Empower Tips, the Thermo brochure, the AppsLab eWorkflow guide) used or defined those terms.
- The one adjacent piece of vendor language found is Chromeleon's "Sequence Data Audit Trail" (quoted in §1 above), which by its name locates an audit trail at the Sequence level, but the source found does not describe what the audit trail contains or whether injection-level events (e.g. reprocessing a single injection) are also captured there vs. elsewhere.

## What I could not establish

1. **Agilent OpenLab CDS / ChemStation** — the entire record hierarchy, instrument-naming model, system-suitability scope, invalidation mechanism, and raw-data definition. Vendor documentation was blocked (HTTP 403 / connection refused) on every URL attempted. Community knowledge-base article summaries surfaced by the search engine were explicitly not used as findings because they could not be attributed to a specific, current, readable vendor page.
2. **Shimadzu LabSolutions** — same, in full. No vendor-hosted technical documentation (manual, help file, or Shimadzu-domain technical note) was located or fetched.
3. **Whether "sequence" (or its Empower/Chromeleon equivalent) is a portable concept across vendors in the sense the question implies.** What was confirmed: both Waters Empower ("Sample Set") and Thermo Chromeleon ("Sequence") use a run-list container above the injection and below the project/eWorkflow-template level, and both document a bracketing concept nested inside that container. Whether this generalizes to Agilent and Shimadzu is unconfirmed given the gaps above — this should be treated as a **two-vendor finding, not a four-vendor finding**, and the question's premise that all four products share a portable "sequence" concept is not verified.
4. **Which level of the Empower or Chromeleon hierarchy carries a guaranteed-unique, human-readable identifier**, as distinct from an operator-entered label. Confirmed only that Chromeleon auto-generates a Sequence name from the eWorkflow name plus a date-time stamp — which is a readable, effectively-unique-in-practice string, but no vendor statement of a uniqueness *guarantee* was found.
5. **Whether the CDS assigns the physical instrument an identity distinct from the lab's own asset tag**, for any of the four vendors, and **whether an instrument can be moved or re-registered between CDS servers**. Not addressed by any source reached.
6. **Any documented "suspect," "voided," or "not for reporting" state on an injection or result**, for any of the four vendors, beyond Empower's "Exclude Faulted" custom-field-summary option (§3), which is a narrower and different mechanism (a summary-calculation option, not a record-state flag).
7. **USP <621> Chromatography and USP <1058> Analytical Instrument Qualification** — not attempted to be fetched in this pass, given the well-known USP-NF paywall; recorded here as an explicit open flank rather than paraphrased from any secondary source. No claim in this report rests on USP <621> or <1058> content.
8. **Public FDA warning-letter or 483 text naming a specific invalidation unit** (e.g. "the sequence," "injections 4 through 12"). Search results surfaced only secondary commentary (LCGC International articles, an ECA Academy news write-up, a compliance blog) discussing warning letters in general terms about system-suitability-triggered OOS invalidation; none of these were fda.gov-hosted warning letter or 483 text, and none is cited as a finding above. This remains open — a direct search of fda.gov's warning letter database for a chromatography/system-suitability case with a stated invalidation unit was not completed in this pass.
9. **Whether Empower's Result Set / Chromeleon's Sequence is the level at which the *audit trail* lives**, versus the injection. Chromeleon names a "Sequence Data Audit Trail" (found, quoted in §1/§4); no equivalent statement was found for Empower, and neither vendor's statement was traced far enough to confirm whether injection-level events are also independently audit-trailed.
