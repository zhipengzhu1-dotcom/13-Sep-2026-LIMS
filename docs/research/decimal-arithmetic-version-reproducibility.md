# Is a locked package-lock.json plus auditable source enough to reconstruct a decimal.js-computed verdict identically five years later, or does something more need recording?

**Asked by:** Ticket #73, "Recording the arithmetic a verdict was computed with" (github.com/zhipengzhu1-dotcom/10-Sep-2026-LIMS/issues/73), following the decimal.js pin decided in ticket #56
**Date:** 2026-09-11
**Status of sources:** decimal.js CHANGELOG.md and package.json were fetched directly from the `master` branch of `github.com/MikeMcl/decimal.js` (raw.githubusercontent.com) and read in full (261 lines, versions 1.0.0 through 10.6.0 — 10.6.0 matches the version pinned in this repo). GitHub issues #26 and #88 were read via the GitHub REST API (issue body + comments), not a secondary write-up. The TC39 `proposal-decimal` README was fetched directly from `github.com/tc39/proposal-decimal` (raw, `main` branch). ASTM E29 could not be reached in a current, non-paywalled form (see below) — consistent with prior scouting on this map. No FDA/GAMP text was found that names a "computation identifier" or "arithmetic version" concept; the CSA-guidance and floating-point-reproducibility claims below are reported as secondary/summarized where no primary full-text was retrievable within the scope of this task.

## Findings

### 1. Has decimal.js shipped a behavior-changing release to its rounding/comparison primitives?

**VERIFIED**, from the full CHANGELOG.md (github.com/MikeMcl/decimal.js/blob/master/CHANGELOG.md):

- **v5.0.4 (14/02/2016) and v5.0.5 (20/02/2016)** — both patch releases fixing GitHub issue #26, "Weird behavior of mod after cloning the constructor" (github.com/MikeMcl/decimal.js/issues/26). The bug: `Decimal.clone(config)` did not handle a config object with some properties omitted — an omitted `modulo` mode was silently interpreted as `0` rather than left at its default, causing `mod()` on a cloned constructor to return a different (incorrect) result than the same operation on the un-cloned constructor for identical inputs (`65 % 40` returned `-15` instead of `25`). The changelog entry for 5.0.5 reads "Bugfix: #26 wrong precision applied." A related second bug surfaced in the same issue thread affecting `acos()`'s internal precision handling via a shared internal `ONE` constant, also patched in this window. These are **patch-version** releases (5.0.3 → 5.0.4 → 5.0.5) that changed the numeric output of existing methods for existing configurations, without any major or minor version bump.
- **v5.0.0 (25/01/2016)** — changed `comparedTo` (the general comparison method) to return `NaN` instead of `null` for comparisons involving `NaN`. This is a behavior change to a comparison primitive, but it shipped at a **major** version.
- **v10.0.0 (10/03/2018)** — "#88 `toNearest` to return the nearest multiple in the direction of the rounding mode." GitHub issue #88 (github.com/MikeMcl/decimal.js/issues/88, PR title "Fix toNearest rounding") describes this as a fix so that `CEIL` and `ROUND_UP` rounding modes actually work in `toNearest`, which had not respected them before. This is a rounding-mode-dependent behavior fix, shipped at a **major** version (9.0.1 → 10.0.0).

No changelog entry across the full history (1.0.0 through 10.6.0) describes a change to `toFixed`, `toPrecision`, `toDP`, `toSD`, or to `ROUND_HALF_EVEN`/`ROUND_HALF_UP` tie-breaking specifically. The confirmed behavior-changing entries found are: the `clone()`-config/`mod()`/precision-propagation bug (patch release), the `comparedTo`/`NaN` change (major release), and the `toNearest`/rounding-mode fix (major release).

### 2. Does decimal.js document a semver/stability policy for rounding behavior specifically?

**VERIFIED (absence)**: The project's README.md (fetched from github.com/MikeMcl/decimal.js/blob/master/README.md) contains no language using the words "semver," "semantic version," "stability," "breaking," or "backward[s] compat[ible]" (checked by direct text search of the fetched file). The CHANGELOG.md does not state a policy either — it is a plain list of per-version changes with no preface describing what triggers a major vs. minor vs. patch bump. package.json declares no `engines` field or stability annotation.

What the version history in Finding 1 *shows*, rather than states: at least one rounding/precision-affecting behavior change (the #26 `clone()`/`mod()` fix) shipped in a **patch** release, and at least two others (`comparedTo`/`NaN`, `toNearest` rounding-mode fix) shipped in **major** releases. There is no declared rule; the one bugfix precedent found landed in a patch release, which is the version-bump level a locked `package-lock.json` would most likely already satisfy without anyone reviewing a diff.

### 3. Precedent for pinning/recording a "computation identifier" separate from the package version

**Could not establish** any GxP, pharma-software-validation (GAMP 5, FDA Computer Software Assurance), or IEEE-754-conformance primary source that names or requires a construct like "arithmetic version," "computation identifier," or "golden-values corpus hash" as distinct from the general software/dependency version.

What was found, reported at the level of confidence available:

- **SECONDARY, general engineering practice, not GxP-specific**: "golden file" / "golden master" regression testing — storing a fixed corpus of input/output pairs and treating a diff against it as the trigger for review — is a documented and widely used pattern in software testing generally (e.g., described in general testing literature retrieved via web search; no single canonical standards document was found defining it). This is a naming convention for a general practice, not evidence that pharma or metrology software validation guidance requires or names it.
- **VERIFIED as an existing artifact, not as GxP precedent**: Berkeley TestFloat (John Hauser, jhauser.us/arithmetic/TestFloat.html) is a real, versioned floating-point conformance test-vector generator/checker used to validate whether an arithmetic implementation conforms to IEEE 754, and its releases (e.g., "Release 3d") are versioned independently of the implementations it tests. This demonstrates the general engineering pattern of a test-vector suite carrying its own version identifier separate from the thing it verifies — but TestFloat is a hardware/software floating-point conformance tool, not a pharmaceutical or laboratory precedent, and no source found ties it to any regulatory framework.
- **Not established**: I could not find FDA Computer Software Assurance guidance text (or GAMP 5 text) that specifically addresses re-verifying a calculation engine's numeric output after a dependency upgrade, as distinct from its general risk-based framework for assessing whether any software change affects a validated function. Search results describing CSA's treatment of vendor patches were summaries from secondary sites (hlc.com, pscsoftware.com, fivevalidation.com, biobostonconsulting.com), not the FDA guidance document itself, and none of them mentioned numeric/arithmetic re-verification or a "computation identifier" concept. I did not attempt to fetch the FDA CSA guidance document itself for this question within the scope given; this should be treated as unverified rather than as evidence the guidance is silent, though nothing in the secondary summaries points toward such a document existing.

### 4. ASTM E29 and the TC39 Decimal128 proposal on reproducibility across implementation versions

- **ASTM E29 — could not establish.** Consistent with prior scouting noted for this map, ASTM E29-22 (and the closely preceding E29-19) remain paywalled at astm.org; only secondary summaries (samaterials.com, labsinus.com, matestlabs.com, a Scribd upload, and an archived 1967 edition on archive.org — itself long superseded and not cited as current) were reachable. None of the accessible secondary material addresses reproducibility across *software implementation versions* at all; they describe the "round half to even" convention and general significant-digit rules only. I made one search pass per the instruction to not spend much effort here, and it did not surface the current standard's full text.
- **TC39 `proposal-decimal` — VERIFIED, checked against the current README on the `main` branch.** The proposal's FAQ contains a section titled "Will Decimal have the same behavior across implementations and environments?" (github.com/tc39/proposal-decimal, README.md, FAQ section). It states that the proposal deliberately does *not* allow environment-dependent precision or rounding-mode defaults, "Decimal is all about avoiding unintended rounding. If rounding behavior depended on the environment, the goal would be compromised... this proposal attempts to find a single set of semantics that can be applied globally," and that "this proposal does not contain any options to set the precision from the environment." This is a cross-*implementation*/cross-*environment* reproducibility guarantee, anchored to a fixed spec (this proposal builds on the fixed IEEE 754-2019 Decimal128 encoding). It is not a statement about cross-*version* reproducibility of a single JavaScript library's own evolving implementation, which is the concern in ticket #73. I found no other reproducibility or conformance language in the document.

I found no such term in any primary source consulted; I did not find evidence it doesn't exist elsewhere, only that it did not surface in the sources searched.
