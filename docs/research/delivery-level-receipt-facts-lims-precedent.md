# In mature open-source LIMS data models, is there an entity above the individual sample container that holds facts about the act of delivery/receipt — and where do receipt condition, discrepancy, rejection, and receiver identity live?

**Asked by:** the orchestrator (Benchline wayfinder map)
**Date:** 2026-09-11
**Status of sources:** Read directly from cloned source, not documentation or blog posts.

- **OpenELIS Global** — `github.com/DIGI-UW/OpenELIS-Global-2`, shallow clone of branch `develop` at commit `b27664ea09c0fdacaf141c4afcc6492f0b099f13` (the tip returned when cloned on 2026-09-11; commit message timestamp shows `2026-09-12`, i.e. this is a live, actively-developed default branch, not a tagged release — a shallow clone carries no tags, so no release number can be cited).
- **SENAITE core** — `github.com/senaite/senaite.core`, branch `2.x` at commit `993f721e6d8494d94a4001cd3d73409504b67a49` (2026-09-10). `setup.py` declares version `2.7.0`. This is the live tip of the default branch.
- **LabKey specimen module, Bika (pre-SENAITE fork), Baobab LIMS** — not reached. LabKey's specimen/study module and Baobab are not vendored anywhere accessible from this environment's network path within the time available, and I did not substitute a documentation page for source; that item is reported as unreached, not answered from a secondary source. Bika LIMS is the direct ancestor of SENAITE and its rejection/schema code is materially the same as what is reported below for SENAITE (SENAITE is a fork of Bika retaining `bika.lims` as its dominant package namespace), so it is not treated as a fourth independent data point.

Both repositories were read as raw source (`.java`, `.hbm.xml`, Liquibase changelogs for OpenELIS; `.py` Archetypes schemas for SENAITE), not as documentation.

## Findings

### 1. OpenELIS Global — `Sample` / `SampleItem`

`Sample` is the accession-numbered thing; `SampleItem` is the container.

- `Sample` — `src/main/java/org/openelisglobal/sample/valueholder/Sample.java`, table `SAMPLE` (`src/main/resources/hibernate/hbm/Sample.hbm.xml:7`). Carries `accessionNumber` (line 39), `receivedTimestamp`/`receivedDateForDisplay` (lines 53–55), `enteredDate`, `collectionDate`, `status`/`statusId`, `clinicalOrderId` (line 73, a link to the ordering encounter, not a delivery record), `referringId`, `sysUserId` (the last system user to touch the row — an audit-log actor, not an attestation field), `consentGiven`/`consentRecordedBy`/`consentRecordedAt` (lines 81–85), and GPS capture fields. **None of `rejected`, `rejectReasonId`, `voided`/`voidReason`, `collector`, `sampleTemperature`, `container`, or `sourceOfSample` live on `Sample`** — those are all on `SampleItem`.
- `SampleItem` — `src/main/java/org/openelisglobal/sampleitem/valueholder/SampleItem.java`, table `SAMPLE_ITEM` (`src/main/resources/hibernate/hbm/SampleItem.hbm.xml:8`), each row `many-to-one` back to one `Sample` (line 30 of the hbm). It carries its own `receivedDate` column (`received_date`, hbm line 83) **separate from** `Sample.receivedTimestamp` — i.e. OpenELIS records receipt at both levels, not only on the parent. It also carries `rejected` (boolean, column `rejected`) and `rejectReasonId` (column `reject_reason_id`, hbm lines 87–89), `sortOrder` (the per-container sequence printed on the specimen label, per the `labNo.sortOrder` convention in the question), `voided`/`voidReason`, `collector`, `collectionConditions`, `sampleTemperature`, `container`, `specimenOrigin`, and (recently added, per in-file comments referencing "Feature 001-sample-management") `remainingQuantity`/`parentSampleItem`/`childAliquots` for aliquoting.
- **Rejection/QA events above the container level**: `SAMPLE_QAEVENT` (`src/main/resources/hibernate/hbm/SampleQaEvent.hbm.xml`) is a join entity carrying `SAMPLE_ID`, `QA_EVENT_ID`, and optionally `sampleitem_id` (nullable per the mapping — the many-to-one is declared but nothing in the mapping enforces it be set), plus `completedDate`/`enteredDate`. `QA_EVENT` itself (`QaEvent.hbm.xml`) is a **catalog of event types** (name, description, category, associated test) rather than a record of an individual receipt discrepancy — it is closer to a controlled vocabulary that `SampleQaEvent` instances point at. So OpenELIS *can* attach a QA event either to the whole `Sample` or to one `SampleItem`, giving it exactly the two levels the question distinguishes, but this is a generic QA-event mechanism, not a receipt-specific entity.
- **Is there anything above `Sample`?** No persistent delivery/order/requester entity was found. `SampleOrderItem` (`src/main/java/org/openelisglobal/sample/bean/SampleOrderItem.java`) looked like a candidate from its name but is a **form-backing DTO** (`implements Serializable`, carries `@NotBlank`/`@Pattern` bean-validation annotations, used by `SamplePatientEntryForm`/`SampleBatchEntryForm`) — it is not a Hibernate-mapped entity and has no table. `Sample.clinicalOrderId` and `referringId` point at an ordering/referral context, not at a delivery-of-a-box-of-containers concept. A `sample_order_override` table exists (`src/main/resources/liquibase/3.5.x.x/100-order-override-record.xml`, added for ticket OGC-1201) recording a deliberate decision to proceed past a control ("ordering without a patient", "continuing after a failed acceptance check") — one row per `sample_id` + `override_type`, with `sys_user_id`, `reason_code`, `reason`, `recorded_date`. This is a per-`Sample` (not per-delivery) attestation-of-a-decision mechanism, closer in shape to what the question calls "the coordinator's I-performed-this-receipt attestation" than the QA-event table is, but it lives at the `Sample` (accession) level, not above it, and it is not itself receipt-specific — its `override_type` values are about ordering/testing decisions.
- A separate `shipment` table exists (`src/main/resources/liquibase/3.5.x.x/shipment-002-create-shipment-table.xml`) with `courier`, `tracking_number`, `shipped_date`, `estimated_delivery_date`, `actual_delivery_date`, `sender_notes`, `receiver_notes`, `status`, `sys_user_id`. This models an **outbound referral shipment** (to another lab, linked via `shipping_box_id`), not inbound receipt of a client's delivery — it is evidence that OpenELIS models "the act of a shipment" as a first-class row when the direction is lab-to-lab referral, but this pattern is not applied to intake.

### 2. SENAITE — `AnalysisRequest`, `Batch`, and the rejection workflow

- `AnalysisRequest` (`src/bika/lims/content/analysisrequest.py`) is the sample. `Batch` (`src/bika/lims/content/batch.py:149`, `class Batch(ATFolder, ClientAwareMixin)`) is a real, separate, folderish content type above it, but it is a **client-facing grouping/billing construct**, not a delivery-receipt entity: its schema fields (`batch.py:60-125`) are `BatchID`, a `UIDReferenceField` to `Client`/`Contact` (~line 73), `ClientBatchID` (line 98), `BatchDate` (line 105), `BatchLabels` (line 114), and `Remarks` (line 125) — no receipt condition, discrepancy, or rejection field of any kind. An `AnalysisRequest` may optionally reference a `Batch` (`BatchID` field on the AR, `analysisrequest.py:1171`) but nothing about receipt is recorded on `Batch`.
- **Rejection is recorded on the `AnalysisRequest` itself**, not on `Batch` and not on a separate rejection entity for the *sample-level* case: `RejectionReasons` is a `RecordsField` on the AR schema (`src/bika/lims/content/analysisrequest.py:666-679`, widget `RejectionWidget`), set via `obj.setRejectionReasons([...])` and then driven through a Bika workflow transition named `reject` (`src/bika/lims/utils/analysisrequest.py:782`, `do_rejection()`, which calls `doActionFor(sample, "reject")`). There is a separate `RejectAnalysis` content type (`src/bika/lims/content/rejectanalysis.py`) but it is the rejection of one **analysis/test result**, not of a sample or container — its schema is `Analysis` schema plus a back-reference `UIDReferenceField('Analysis', allowed_types=('Analysis',))` to the analysis it replaces; it has no bearing on container-level or delivery-level receipt.
- The rejection UI lives in `src/senaite/core/browser/samples/rejection/reject_samples.py`; the reasons vocabulary is a single site-wide setup field (`RejectionReasons` on `BikaSetup`, `src/bika/lims/content/bikasetup.py:1195-1200`, exposed via `isRejectionWorkflowEnabled()` at line 1345 and `getNotifyOnSampleRejection()`), not a per-delivery configurable list.
- **Who received, and is it verified separately?** `DateReceived` is a stored field on the AR (`analysisrequest.py:1068`, `write_permission=FieldEditDateReceived`). There is **no stored "Receiver" field** — `getReceivedBy()` (`analysisrequest.py:2286-2291`) does not read a persisted attribute at all; it derives the receiver from Plone's workflow history by finding the actor of the `receive` transition (`getTransitionUsers(self, 'receive', last_user=True)`). The same pattern is used for verification: `getDateVerified()` (line ~2294) reads the timestamp of the `verify` transition from workflow history, and the actor of the `reject` transition is read the same way a few lines above `getReceivedBy` (`analysisrequest.py:2280-2284`, an `actor = items.get('actor')` lookup keyed to `action != 'reject'`). So in SENAITE, "who performed the receipt" and "who verified it" are **not modelled as domain fields at all** — they are read out of the generic Plone workflow/audit-trail history, keyed by transition name, and are not distinguishable from any other user action taken against that content object except by which transition fired.
- `SampleCondition` (`src/bika/lims/content/samplecondition.py`, `src/senaite/core/content/samplecondition.py`) is a separate, small controlled-vocabulary content type; the AR references it via a `UIDReferenceField('SampleCondition', allowed_types=('SampleCondition',))` (`analysisrequest.py:891-895`). It records *what condition was selected*, not an event of who observed it or when — that provenance again falls back to workflow history if it exists at all.

### 3. Partitions — duplicated or shared?

SENAITE's `create_partition()` (`src/bika/lims/utils/analysisrequest.py:653-733`) answers this directly from the copy mechanism, not from naming convention alone. It copies **almost every field** from the primary AR into the new partition via `fields_to_dict(ar, partition_skip_fields)` and only *excludes* a fixed list (`partition_skip_fields`, lines 666-694): `Analyses`, `Attachment`, `Client`, `DetachedFrom`, `Profile(s)`, **`RejectionReasons`**, `Remarks`, `ResultsInterpretation(Depts)`, `Sample`, `Template`, `ParentAnalysisRequest`/`PrimaryAnalysisRequest`, plus Plone's own `id`/`description`/dates/etc.

That means:
- **`RejectionReasons` is explicitly excluded from the copy** — a rejection recorded on the primary AR is not propagated to a partition created from it (nor, by the same mechanism read in reverse, would rejecting a partition write back to the primary). Rejection is per-AR, and partitioning does not fan it out.
- **`DateReceived` and `Sampler` are *not* in the skip list**, so they are copied — i.e. **duplicated** — onto every partition at creation time. This is a positive finding of duplication: SENAITE does not store receipt facts once on a parent and reference them from children; it stamps a copy onto each partition object at the moment the partition is created. If `DateReceived` were later corrected on the primary, nothing in this code path suggests the partition's copy would be updated — `create_partition` runs once, at creation.
- Partition naming follows a documented `{parent-id}-P{nn}` convention (referenced in `src/senaite/core/content/senaitesetup.py:1239`, "Per-parent partition counter"), but the exact ID-generation call site was not located in the time available; this is reported as a gap, not inferred.

For OpenELIS, §1 above already answers this from schema: `SampleItem.receivedDate` is a real, distinct column per container row, not a copy of `Sample.receivedTimestamp` — both levels are populated independently, so there is no single source of truth for "when was this container received" once a `Sample` has more than one `SampleItem`. `SampleItem.rejectReasonId`/`rejected` exist per row with no equivalent field on `Sample` to aggregate them; a delivery-wide discrepancy affecting every container would have to be written to every `SampleItem` row individually or attached once to the parent `Sample` via a `SAMPLE_QAEVENT` row with `sampleitem_id` left null (the mapping allows this; nothing in application code reviewed here confirms it is actually used that way for receipt discrepancies specifically, since `QaEvent` is a generic test/event catalog rather than a receipt-specific one).

### 4. A system with an explicit receipt/accessioning record distinct from the specimen

**None found** in either codebase read. OpenELIS's `shipment` table (§1) is the closest thing to "the act of receipt" as a first-class row with its own actor and status, but it models outbound *referral* shipments between labs, not inbound receipt of a client's delivery — the direction the question asks about. Neither OpenELIS nor SENAITE has a table/content-type whose purpose is "the event of this delivery arriving," distinct from the sample/container rows the delivery produced. LabKey's specimen module and Baobab LIMS were not reachable from this environment and are not reported on.

### 5. Counter-evidence (both duplication and no-place-for-it patterns confirmed)

- SENAITE **duplicates** `DateReceived` (and other non-skip-listed fields, e.g. `Sampler`) across every partition row created from a primary AR — confirmed from the `partition_skip_fields` list, not inferred (§3).
- SENAITE has **no place at all** for "who received it" as a domain fact — it is read out of the Plone workflow history by transition name (`getReceivedBy`, `getDateVerified`), which is a generic audit log, not a modelled attestation. If that history were ever purged or the transition renamed, the fact would be unrecoverable through the documented accessor.
- OpenELIS **duplicates receipt** in the literal sense that `receivedDate` exists as a real column on both `Sample` and every `SampleItem`, with no code path shown here that keeps them in sync.
- OpenELIS's rejection/discrepancy machinery (`rejected`/`rejectReasonId`) is **per-container only**; a delivery-wide discrepancy has no dedicated column on `Sample` and must either be pushed to every `SampleItem` row or attached via a generic `SAMPLE_QAEVENT` row that is not receipt-specific.
- Neither system has an entity that models "a discrepancy raised before any accession/lab number is assigned" — both `Sample`/`AnalysisRequest` already presuppose the accession/AR exists before rejection or a QA event can be recorded against it. Whether either system supports refusing a delivery before it becomes a row at all was not established (see below).

## What I could not establish

- Whether OpenELIS or SENAITE support the specific scenario in Benchline's archetype procedure — a discrepancy raised **before** any accession number / lab number is assigned, such that a refused delivery never becomes a `Sample`/`AnalysisRequest` row at all. Nothing read in either codebase models a pre-accession discrepancy record; both systems' rejection mechanisms operate on an already-created accession. This may mean neither system supports that scenario, or it may mean the relevant code (e.g. a pre-registration intake screen) exists elsewhere and was not found — I did not do an exhaustive search of both repositories' UI/controller layers, only their content/schema/workflow layers most directly relevant to the question.
- The exact SENAITE partition-ID generation code (`{parent_id}-P{nn}`) — confirmed as a documented convention (`senaitesetup.py:1239`) but the generator call site was not located.
- LabKey's specimen module and Baobab LIMS — not reached at all in this environment; no finding, positive or negative, is reported for either.
- Whether OpenELIS's `SAMPLE_QAEVENT.sampleitem_id` being nullable is actually exercised in the receipt/discrepancy workflow (as opposed to only in result-level QA events) — the mapping permits a `Sample`-only QA event, but I did not trace the service/DAO layer to confirm the intake UI ever creates one that way.
- Whether either system's `sysUserId`/workflow-actor mechanism would satisfy an auditor's requirement for a **distinguishable attestation** ("I performed this receipt") as opposed to an incidental last-touch/last-transition actor — this is a question of interpretation the source code does not settle either way; both systems record an actor, but as a side effect of a generic audit mechanism rather than a dedicated "receipt performed by" field.
