# What does the documented evidence say about storing ~12,000–30,000 immutable rendered PDF documents per year, alongside an operational SQLite database that is already under concurrent load?

**Asked by:** the orchestrator (document/report storage sizing question, following on from issue #17 persistence/concurrency and issue #15 performance budget)
**Date:** 2026-09-11
**Status of sources:** All SQLite vendor pages fetched live on 2026-09-11 and checked for the version/hardware/date they document (none carry a "superseded" banner as of this date). Node.js documentation fetched live against the currently-documented version (v26.8.2, `node:sqlite` at Stability 1.2 "Release candidate"). One repository file (`open-lims-module-scope-inventory.md`) read directly rather than re-derived, per instruction. PDF-size figures are the weakest category of source here and are flagged as such throughout — see §3 and "What I could not establish."

## Findings

### 1. SQLite's own position on internal vs. external BLOB storage

- **Crossover point.** `https://www.sqlite.org/intern-v-extern-blob.html` (fetched 2026-09-11) states the crossover for *read* performance is **~100KB**: below that, storing the BLOB inside the database (a row) reads faster than a separate file; above it, the filesystem wins. Ratios are given per page size, e.g. at an 8192-byte page size, 100KB BLOBs still favour internal storage (ratio 1.035) while 200KB BLOBs favour external storage (ratio 0.830).
- **What was actually measured.** The page's own data is: random-order **reads only** (no write benchmark) against a 100MB database, BLOB sizes 10KB/20KB/50KB/100KB/200KB/500KB/1MB, page sizes 1024–65536 bytes, on a **circa-2011 Ubuntu workstation, ext4, SATA disk, SQLite 3.7.8**. This is a 15-year-old measurement on an unspecified vintage of hardware and does not test writes, WAL mode, or concurrent access at all — it predates WAL's typical production tuning discussions and the `synchronous=FULL` question entirely.
- **"35% Faster Than The Filesystem."** `https://www.sqlite.org/fasterthanfs.html` (fetched 2026-09-11) documents the 35% figure for **small blobs, 8–12KB (10KB average, uniformly distributed)**, tested with 100,000 blobs across five machines (2009 Dell/Win7, 2016 Lenovo/Win10, 2015 MacBook Pro, an Ubuntu 16.04 desktop, and a Galaxy S3/Android). The page states explicitly: "The 35% figure is approximate," results vary substantially by hardware/OS, cold-cache runs perform worse, "the filesystem will generally be faster for larger blobs, since the overhead of open() and close() is amortized over more bytes of I/O," and on Android SQLite writes were *slower* than direct filesystem writes. **Neither vendor page supports a claim of internal-storage advantage for hundred-KB-to-megabyte PDFs** — both explicitly describe the advantage as shrinking or reversing as size grows past roughly 100KB.
- **Limits.** `https://www.sqlite.org/limits.html` (fetched 2026-09-11): `SQLITE_MAX_LENGTH` (max BLOB/string length) **defaults to 1,000,000,000 bytes (1GB)**, with a hard ceiling of 2³¹−3 (~2.147GB); it is compile-time/runtime configurable downward. Max database size given page-count and page-size limits is documented at up to ~281TB (2³²−2 pages × 65536-byte pages); with the more realistic default page size (4096 bytes) that page's own arithmetic yields ~17.5TB. None of these ceilings is close to being approached by 12,000–30,000 PDF-sized rows per year.
- **`appfileformat.html` / SQLite Archive (`sqlar`).** `https://www.sqlite.org/appfileformat.html` (fetched 2026-09-11) makes the general case for SQLite-as-container-format and states that a compressed SQLite Archive is size-comparable (±1%) to an equivalent ZIP, with the specific advantage that **individual entries can be updated without rewriting the whole archive** — relevant to "add a new report row" workloads, but this is a general design argument, not a benchmark against filesystem storage for this specific size class, and it does not address WAL or concurrent-reader behaviour at all.

### 2. Interaction with WAL and checkpoint starvation; incremental BLOB I/O in `node:sqlite`

- **WAL growth is proportional to changed data.** `https://www.sqlite.org/wal.html` (fetched 2026-09-11): "A large change to a large database might result in a large WAL file... in the meantime, the file can grow very big." As of SQLite 3.11.0 (2016), a single transaction's WAL footprint is proportional to the transaction itself (each changed page written once per transaction, not once per statement). A multi-hundred-KB PDF written as one BLOB in one transaction therefore adds roughly that many bytes (rounded up to whole pages) to the WAL exactly once per write — it is not documented to cause disproportionate WAL bloat *by virtue of being a BLOB*, but it is additional write volume like any other write of that size.
- **This does interact with the already-documented checkpoint-starvation problem.** The same page confirms the mechanism cited in the prior decision: "A checkpoint can run concurrently with readers, however the checkpoint must stop when it reaches a page in the WAL that is past the end mark of any current reader," and "if a database has many concurrent overlapping readers and there is always at least one active reader, then no checkpoints will be able to complete and hence the WAL file will grow without bound." `wal_autocheckpoint` defaults to a 1000-page (~4MB at 4096-byte pages) threshold to trigger automatic checkpoint attempts, but that trigger does not guarantee completion under sustained readers. **What follows directly from this documentation:** adding report-write transactions of a few hundred KB each does not change the *mechanism* of checkpoint starvation (readers block checkpoints regardless of what's being written), but it does raise the WAL growth rate per write compared with small transactional rows, which — under the already-identified ~20-sustained-reader starvation scenario — means the WAL file's unbounded-growth alarm threshold would be reached sooner, in proportion to bytes written. I did not find a documented numeric relationship (e.g., "X MB/hour of WAL growth causes Y") — this is a mechanism finding, not a rate finding.
- **`node:sqlite` `DatabaseSync` has no incremental/streaming BLOB interface.** Current Node.js documentation (`https://nodejs.org/api/sqlite.html`, fetched 2026-09-11, documenting Node v26.8.2; `node:sqlite` is Stability 1.2 "Release candidate," added v22.5.0, promoted from experimental in v23.4.0/v22.13.0 and to release-candidate in v25.7.0) shows binding accepts `TypedArray`, `DataView`, `ArrayBuffer`, `SharedArrayBuffer`, or `Buffer`, and returns BLOB columns as a fully-materialized `Uint8Array`. There is **no exposure of SQLite's `sqlite3_blob_open`/incremental-BLOB-I/O C API** in `node:sqlite`. Consequently, every read or write of a stored PDF must hold the entire document in memory as a Buffer/Uint8Array at some point; there is no way to stream a large BLOB in chunks through this API.

### 3. Typical size of a rendered PDF of a one-to-few-page tabular document

This is the softest figure in this report — I could not find controlled, source-cited benchmarks for "simple table page" PDF size, only scattered comparative numbers.

- A Puppeteer maintainer issue thread (`https://github.com/puppeteer/puppeteer/issues/2440`, "PDF file size is unexpectedly high," retrieved 2026-09-11) reports **user-observed** comparisons of Puppeteer-generated single-page PDFs against PhantomJS-generated equivalents: examples cited in that thread are roughly **80KB vs. 36KB** for one page and **1,019KB vs. 391KB** for another, with the reporter's own diagnosis (via Acrobat Pro's space audit) attributing the difference to **font embedding**, even when only standard fonts (Arial, Times New Roman) were used without custom web fonts. This is a single bug-report thread, not a benchmark suite, and the "another page" example is not characterised as tabular.
- Vendor/tooling documentation for `pdfkit` (`https://pdfkit.org/docs/text.html`, `https://deepwiki.com/foliojs/pdfkit/3.4-fonts-and-embedding`, retrieved 2026-09-11) confirms `pdfkit` **subsets embedded fonts** — only glyphs actually used are embedded — which is a mechanism that would tend to keep output smaller than a full-font-embedding renderer, but no absolute size figures for a representative table page were published on the pages I could reach.
- **My own arithmetic extrapolation (not a source figure, shown with inputs):** taking the Puppeteer issue-thread numbers as one anecdotal proxy — roughly 40–100KB for a plain single-page document rendered by a Chromium-based tool with standard-font embedding, and materially less (tens of KB) for a `pdfkit`/`pdf-lib`-style generator with font subsetting — a rough planning range of **~30KB–300KB per issued report document** would not be unreasonable to carry forward, with headless-Chrome tools trending toward the upper part of that range because of font-embedding overhead and non-Chromium generators trending toward the lower part. **This range is not independently verified; it is an inference from a small number of anecdotal data points, not a measured benchmark, and should be labelled soft.**
- Applying the ticket's own volume figures as arithmetic (inputs: ~1000 samples/month, ~12,000 reports/year stated in the ticket, and the 30KB–300KB soft range above): 12,000 × 30KB ≈ **360MB/year**; 12,000 × 300KB ≈ **3.6GB/year**; the ticket's stated upper document count of 30,000/year (amendments included) at the same per-document range gives **900MB–9GB/year**. These are arithmetic extrapolations from an unverified size range, not measurements, and are shown only to make the scale of the "hundreds of MB to single-digit GB per year" question visible — they should not be read as a sizing conclusion.

### 4. Backup implications

- **Online Backup API.** `https://www.sqlite.org/backup.html` (fetched 2026-09-11) describes `sqlite3_backup_init()`/`_step()`/`_finish()` as a mechanism to copy a live database to another file while the source stays readable/writable by other connections, taking only brief locks per step, and working even for in-memory source databases. The documented pattern for concurrency-friendly backup is to call `sqlite3_backup_step()` in small page batches (the manual page's own example: 5 pages at a time) with a sleep between batches to release locks, which **trades backup duration for reduced contention** — i.e., backup duration is not fixed but is a function of database size divided into batches, each batch competing for locks with live writers. The API copies pages incrementally and thus scales with total database size; the documentation does not give a throughput number (pages/second) to convert that into wall-clock time — that number is deployment- and hardware-specific and not stated on the page.
- **`VACUUM INTO`** is mentioned on the same page as a newer alternative that produces a vacuumed copy of a live database into a separate file; the backup.html page does not elaborate further on its locking behaviour or performance characteristics; I did not separately fetch `https://www.sqlite.org/lang_vacuum.html` for this report and note that as a gap.
- **`node:sqlite` does expose a backup facility.** Current Node docs (`https://nodejs.org/api/sqlite.html`, fetched 2026-09-11) document a module-level `sqlite.backup(sourceDb, path[, options])` function returning a `Promise`, with a `progress` callback reporting `{ remainingPages, totalPages }`. The documentation describes this as wrapping the C `sqlite3_backup_init`/`_step`/`_finish` sequence — i.e., it exposes the Online Backup API's incremental, concurrency-tolerant semantics, not a plain file copy.
- **Implication for a growing PDF-bearing database, stated as documented mechanism only:** because backup duration scales with total database size and copies proceed page-by-page under the same reader/writer locking rules as ordinary access, a database whose size is growing by hundreds of MB to several GB per year from stored PDFs (per §3's soft arithmetic) will have a backup operation whose duration grows correspondingly, and that backup operation will contend for the same locks that already govern checkpoint progress and reader/writer concurrency — but the SQLite documentation does not give a duration-per-GB figure, so I cannot turn this into a stated number.

### 5. What comparable systems do, beyond what `open-lims-module-scope-inventory.md` already records

That file (read directly, not re-derived: `docs/research/open-lims-module-scope-inventory.md`, §A.2 item 13 and §B.2 item 13) already establishes that SENAITE's `ResultsReport` content type carries a `Pdf` blob field and OpenELIS's unreleased `compliance` module's `ComplianceReportArchive` JPA entity has `pdf_content byte[] NOT NULL` plus `sha256_hash CHAR(64) NOT NULL`. Reading the same source material again specifically for size/performance commentary and hashing scope, beyond what is already recorded there:

- **No size or performance concern is documented by either project for the blob-storage choice itself.** Neither the SENAITE source comments captured in that file (`src/senaite/core/content/resultsreport.py`, `src/senaite/impress/storage.py`) nor the OpenELIS `compliance` module source (`ComplianceReportArchive`, `ComplianceReportArchiveServiceImpl`) as described in that inventory file contain any comment, changelog entry, or documented caveat about PDF blob size, database growth, or backup/checkpoint impact. This is an absence, not a statement that it was considered and dismissed — I did not find the topic raised at all in either codebase as surfaced by that inventory.
- **Hashing: only OpenELIS's unreleased module hashes, and it hashes the whole PDF byte array.** Per the inventory file, `ComplianceReportArchive.sha256_hash CHAR(64) NOT NULL` is populated by `ComplianceReportArchiveServiceImpl`, described there as hashing on first archive-write (`archiveIfAbsent()`), over the `pdf_content byte[]` column — i.e., a SHA-256 (64 hex chars matches SHA-256's 32-byte/64-hex-char digest) computed over the full rendered PDF bytes, used together with a unique `(sample_id, amendment_number)` constraint and an if-absent-only write path to make re-archival a no-op rather than an overwrite. SENAITE's `ResultsReport.Pdf` field, per the same file, has **no accompanying hash field documented** — integrity there rests entirely on Plone/Zope's object model never providing an update path (new object per publish), not on a checksum.

## What I could not establish

- **A rate (bytes/hour or similar) at which additional PDF-write volume worsens WAL growth under the specific ~20-reader starvation scenario already documented for this project.** SQLite's WAL documentation confirms the mechanism (checkpoints blocked by any active reader; WAL grows unboundedly in that condition) but gives no formula relating write volume to how fast the file grows past any particular size, so I can state the mechanism but not a number.
- **A controlled, source-cited benchmark for "PDF size of a simple 1–3 page tabular document."** I found one bug-report thread with anecdotal before/after numbers and general statements about font-subsetting behaviour in `pdfkit`, but no vendor or independent benchmark specifically for tabular lab-report-style content. The 30KB–300KB range in §3 is my own inference from thin evidence and is explicitly flagged as soft; a real measurement against Benchline's own rendering stack would be needed to replace it.
- **`VACUUM INTO`'s locking and performance behaviour in detail** — I did not fetch `lang_vacuum.html` and relied only on the one-sentence mention in `backup.html`.
- **A stated throughput figure (pages/second or MB/second) for `sqlite3_backup_step` / the `node:sqlite` `backup()` function**, needed to convert "backup scales with database size" into an actual duration estimate. Neither the SQLite backup API page nor the Node.js `node:sqlite` documentation states one; it is necessarily hardware- and contention-dependent and not documented as a fixed number anywhere I found.
- **Whether SENAITE or OpenELIS deployments have ever hit a practical size or performance ceiling from storing PDFs as blobs.** Neither project's available documentation (as already surfaced in the inventory file) discusses this, and I did not find issue-tracker discussion of it in the sources reviewed for this report; absence of documented concern is not evidence that no concern exists in practice.
