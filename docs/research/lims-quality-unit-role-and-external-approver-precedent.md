## Findings

### 1. SENAITE's role enumeration has no QA/quality-unit role, and the one "external inspector" role that existed is being deleted

The current rolemap (`src/senaite/core/profiles/default/rolemap.xml:5-31`, HEAD `993f721e`) lists these SENAITE-specific roles:

```
Analyst, Client, LabClerk, LabManager, Preserver, Publisher, Sampler,
SamplingCoordinator, Verifier, ClientGuest
```

This is *not* the same list previously verified in `docs/research/lims-role-models-and-separation-of-duties.md`, which also included `RegulatoryInspector` — and that is a currency finding in its own right. At the current HEAD, `RegulatoryInspector` has been removed from `rolemap.xml` entirely (it is absent from the file; confirmed by `grep -rn "RegulatoryInspector"` across the whole tree, which returns zero hits inside `rolemap.xml`). The removal is an explicit, in-progress upgrade step for the unreleased 2.7.0 line: `src/senaite/core/upgrade/v02_07_000.py:179-215`, function `remove_regulatory_inspector_role`, docstring: *"Remove the obsolete 'RegulatoryInspector' role and group... 1. Drop the role from the portal_role_manager... 2. Remove the RegulatoryInspectors group... 3. Drop the role from the portal's known roles."* `CHANGES.rst:37` records this as `#2962 Remove the obsolete RegulatoryInspector role`. Because the last tagged release (2.6.0, 2025-04-04) still shipped `RegulatoryInspector` and this HEAD does not, any claim about SENAITE's role list must state which point in time it is checked at — I checked HEAD (2026-09-10 commit) and the removal is real, unreleased, and irreversible-by-design (the upgrade step deletes existing assignments on upgrade, not just the definition).

I searched `rolemap.xml`, and every file under `src/senaite/core/profiles/default/workflows/`, for the strings `QA`, `Quality`, `quality unit`, `Approver`, `Reviewer` (SENAITE-specific, not the inherited Plone `Reviewer` base role which is also in the file but unused by any SENAITE-specific permission grant), and found: **no SENAITE-specific role named for a quality unit, QA function, or a role that approves specifications or methods, distinct from `LabManager` or `Verifier`.** `LabManager` and `Verifier` are the only roles granted `senaite.core: Transition: Verify`-class permissions (this is consistent with, and does not add to, the separation-of-duties file's earlier finding that verification is a role/identity check, not a QA-department check).

### 2. `Client` and `ClientGuest` — two different external-party precedents, one editable, one strictly read-only

**`Client` is not read-only.** I grepped the full permission-grant table in `rolemap.xml` programmatically for every `<permission>` block that names the `Client` role. It is granted `View`, `Access contents information`, `List folder contents`, `senaite.core: View Navigation`, and **21 separate `senaite.core: Field: Edit *` permissions** on sample-level fields, including `Edit Batch`, `Edit Client Reference`, `Edit Priority`, `Edit Sample Point`, `Edit Sample Type`, `Edit Specification`, `Edit Sampling Date`, `Edit Sampling Deviation`, `Edit Remarks`, `Edit Template`, `Edit Preservation`, `Edit Environmental Conditions`, `Edit Container`, `Edit Composite`, `Edit Contact`, `Edit Date Sampled`, `Edit Client Order Number`, `Edit Client Sample ID`, `Edit Client`, `Edit Sample Condition` — `rolemap.xml:394-591` (exhaustive list confirmed by a script that parsed every `<permission name=... >...</permission>` block and reported which ones name `Client`). So the `Client` role, as a *global* role grant, is an editable-field external-party account, not a read-only one.

**`Client` is, however, granted zero workflow-transition permissions.** I ran the same block-parsing check restricted to permission names containing `Transition` and found **no `senaite.core: Transition: *` permission grants the `Client` role anything**, at HEAD (verified by script, zero matches). The one apparent exception is explained by a code comment, not a role grant: `senaite_sample_workflow/definition.xml:1621` says *"'cancel' transition can be triggered by Client before the sample gets received"*, but the `cancel` transition's guard (`definition.xml:1407-1415`) requires `senaite.core: Transition: Cancel Analysis Request`, which in `rolemap.xml:831-836` is granted to `LabClerk`, `LabManager`, `Manager`, and `Owner` — **not** `Client`. The mechanism is `Owner`, a Plone local role granted to a Contact's linked user on their own sample object (`contact.py:308`, `sec_api.grant_local_roles_for(self, roles=["Owner"], user=user)`, already established in `lims-role-models-and-separation-of-duties.md`). So a Client-side account's ability to cancel is a local-`Owner`-on-own-object grant, not a transition permission attached to the global `Client` role.

**`ClientGuest` is genuinely read-only.** Its only permission grants in the whole rolemap are `View`, `Access contents information`, `List folder contents` (`rolemap.xml`, confirmed by the same script — zero `Field: Edit` or `Transition:` grants). It exists specifically for cross-client sharing: `src/senaite/core/behaviors/clientshareable.py:38-64` defines a `clients` field with the doc comment *"This content will become available on searches to users that belong to any of the selected clients thanks to the role 'ClientGuest'"*, and the dynamic-local-role adapter that assigns it, `src/senaite/core/adapters/localroles.py:117-148` (`ClientShareableLocalRoles.getRoles`), returns `["ClientGuest"]` only if the requesting user's `Contact` belongs to a client the object has explicitly been shared with. This is the read-only external-account precedent the ticket asked about: a named role, granted to an account (not to "nobody"), constrained at the rolemap level to view-only permissions, and applied per-object rather than globally.

### 3. No non-user approver field found on SENAITE's method or analysis-service content types

I grepped `src/bika/lims/content/analysisspec.py`, `src/bika/lims/content/abstractbaseanalysis.py`, and `src/bika/lims/content/method.py` for `approv`, `authoris`, `authoriz`, `signed_by`, `sign_off`, `reviewed_by` and found exactly one hit: `abstractbaseanalysis.py:487-497`, a plain `Accredited` `BooleanField` with the comment *"True if the accreditation body has approved this lab's method for accreditation"*. This field records only a yes/no flag — **there is no accompanying field for who approved it, when, or which accrediting body**, on the `AnalysisService`/`AbstractBaseAnalysis` schema at this HEAD. `src/senaite/core/content/method.py` (the current `Method` content type, 13KB, all fields enumerated by grepping every `= ...Field(` assignment) has fields for `instructions`, `instruments`, `calculations`, `calculation` and no others relevant to approval or versioning — consistent with the already-established fact (senaite/senaite.core PR #1708) that `AnalysisService` versioning was removed; I did not re-verify the PR itself, only that the current `Method` schema carries no approval-attribution field of any kind.

**A genuine non-account approver does exist for published reports, but it is a department manager, not a specification/method approver.** SENAITE's report layer (`senaite.impress`) renders a "Responsibles" signature block from `AnalysisRequest.getResponsible()` (`src/bika/lims/content/analysisrequest.py:1732-1765`), which walks each sample's `Department` objects and calls `department.getManager()` (`src/senaite/core/content/department.py:160-175`, a `UIDReferenceField` to a `LabContact`). A `LabContact` is a distinct content type from a Plone/Zope user account, and it is **not required** to have one: `src/bika/lims/content/labcontact.py:163-169`, `hasUser()`:
```python
def hasUser(self):
    """Check if contact has user"""
    username = self.getUsername()
    if not username:
        return False
    user = api.get_user(username)
    return user is not None
```
This means a Department's designated Manager — the person whose name, salutation, job title and (if present) scanned signature image appear on a published Certificate of Analysis via `senaite.impress`'s `signatures.pt` template (`src/senaite/impress/analysisrequest/templates/signatures.pt:5-40`, rendering `manager/Salutation`, `manager/Fullname`, `manager/JobTitle`, and an `<img>` of `manager/Signature`) — **can exist with no linked login account at all.** This is the clearest instance I found in either codebase of an approver/signer on a customer-facing document who is not necessarily a system user. It is scoped to the report signature block, not to specification or method approval, and it is a per-Department, not per-report, designation (the report just aggregates all Departments touched by the sample's analyses).

### 4. OpenELIS's electronic-signature model: the signer must always be an existing `system_user`, and no role check gates who may sign

`ElectronicSignatureServiceImpl.java` (`src/main/java/org/openelisglobal/esig/service/ElectronicSignatureServiceImpl.java`, 416 lines) is explicitly annotated *"Service implementation for electronic signatures per 21 CFR Part 11"* (line 27-28). Its `executeSignature(...)` method (lines 66-onward):
- Looks the signer up strictly by username against the application's own user store: `SystemUser user = systemUserService.getDataForLoginUser(username); if (user == null) { throw new IllegalArgumentException("User not found: " + username); }` (lines 88-91).
- Requires a prior "first-use certification" (`isUserCertified(username)`, line 94-96) and credential re-verification (`verifyCredentials`, line 99) — both keyed to the same username.
- Contains **no role or permission check** anywhere in the file (I grepped the file for `role|Role|permission|Permission` and got zero matches) — any authenticated, certified user who can present valid credentials may sign, regardless of whether they hold a QA-type role. Authorization is therefore identity- and certification-gated, not role-gated, at this layer.

The persisted entity, `src/main/java/org/openelisglobal/esig/valueholder/ElectronicSignature.java`, enforces the same constraint structurally: `signerId` is `@NotNull` and documented as *"Foreign key to system_user. The user who executed the signature."* (lines 50-56); `signerNamePrinted` is a denormalized copy of the name at signing time, explicitly *"for compliance — name changes don't alter historical records"* (lines 58-64), but it is a snapshot of a user's name, not an independent free-text field that could name a non-account party. **I could not find any code path, field, or comment in the `esig` package suggesting a signature can be attributed to anyone other than an existing `system_user` row.** I searched the whole `esig` package tree for `external`, `guest`, `non-user`, `free.?text` (case-insensitive) and found no hits.

### 5. OpenELIS's shipped role list has no QA/quality role — "QA" exists only in a test fixture, not in the seeded database

The canonical, shipped role enumeration is the `COPY clinlims.system_role (...) FROM stdin` block in `db/dbInit/OpenELIS-Global.sql:16890-16906` (also present verbatim in `install/installerTemplate/linux/initDB/OpenELIS-Global.sql`, `dev/database/dbInit/OpenELIS-Global.sql`, and `volume/database/dbInit/OpenELIS-Global.sql` — I diffed none of these against each other but all four paths contain the identical `COPY` header). The seeded roles are:

```
Results modifier, Audit Trail, Test Management, Intake, Inventory mgr,
Maintenance Admin, Reports, Results entry, User Admin, Validator,
Results Admin, Identifying Information Edit,
Hematology/Immunology/Serology/Biochemistry/Virology automatic
```

plus later-added roles confirmed in Liquibase changesets outside this seed file: `Reception` (`src/main/resources/liquibase/2.6.x.x/update_roles.xml:182-215`, and again in `src/main/resources/liquibase/3.5.x.x/shipment-007-add-menu-and-role.xml:82-95`), `Global Roles`, `Lab Unit Roles`, `Global Administrator` (`3.5.x.x/045-manual-entry-permissions.xml:87`). **None of these seeded or Liquibase-added roles is named for a QA function or a quality unit.** The closest functional match is `Validator` (*"A person who can validate results"*) and `Results Admin` (*"Able to access all results forms"*) — both are laboratory-operations roles, not quality-unit roles, by their own descriptions.

A role literally named `QA` (`description="Quality Assurance"`) **does exist**, but only in `src/test/resources/testdata/user-role.xml:23-24`, a JUnit/integration test fixture, alongside a smaller, clearly synthetic role set (`Admin`, `LabTech`, `Manager`, `QA`) that does not match the production seed list above. I grepped every Liquibase changeset under `src/main/resources/liquibase/` for `'QA'` as a `system_role.name` value and found no hits outside test resources. **I am reporting `QA` as a role name that appears in OpenELIS's own test fixtures (evidence that its authors modeled the concept for testing) but not as a role that ships in the product's seeded database at this HEAD or in the 2.6.x/3.5.x Liquibase role-management changesets I checked.** This is a deliberately narrow claim — I did not check every Liquibase directory (there are many versioned subdirectories) for a `QA` insert, so absence from the *ones I checked* is not proven absence from the entire changeset history.

### 6. No shared/anonymous read-only account concept found in OpenELIS

I grepped `src/main/java/org/openelisglobal/systemuser/` and `src/main/java/org/openelisglobal/login/` for `READ_ONLY`, `read-only`, `readonly`, `guest`, `Guest`, `external user`, `ExternalUser` and found zero hits in either package. **I could not establish that OpenELIS Global has any shared, anonymous, or explicitly read-only account concept comparable to SENAITE's `ClientGuest`.** This is reported as an absence from the packages searched, not a claim that no such mechanism exists anywhere in a ~400k-line Java/Spring codebase I did not fully traverse.
