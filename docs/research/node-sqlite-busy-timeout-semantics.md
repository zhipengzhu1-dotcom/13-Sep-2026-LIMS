# Contended write cost: what does `node:sqlite`'s `timeout` actually do, and does it survive measurement?

**Asked by:** ticket #31, "Contended write cost: does the persistence decision survive measurement?" (https://github.com/zhipengzhu1-dotcom/10-Sep-2026-LIMS/issues/31)
**Date:** 2026-09-11
**Status of sources:** Checked against the Node.js v24.x API docs (the running version, v24.15.0) and against a beta build of the same page (`beta.docs.nodejs.org/sqlite.html`) that carries per-option "Added in" history; cross-checked the current `nodejs/node` `v24.15.0` tag source for the bundled SQLite header (`deps/sqlite/sqlite3.h`); checked the upstream `sqlite3_busy_timeout()` reference and the WAL document on sqlite.org; checked sqlite.org's own changes.html for the 3.51.3 changelog entry. I did not find a version-specific archived copy of the Node v24.15.0 docs page separate from the current `nodejs.org/api/sqlite.html` (which now serves v26.8.2); where a quote is sourced from that live page rather than the beta v24 mirror, I've marked it as "confirmed stable across v24→v26," not as v24-specific text.

## Findings

**1. What `timeout` does, and its default**

The `DatabaseSync` constructor option `timeout` is documented as:

> "The busy timeout in milliseconds. This is the maximum amount of time that SQLite will wait for a database lock to be released before returning an error. **Default:** `0`."

This is stated to be a wrapper around SQLite's `sqlite3_busy_timeout()` (https://sqlite.org/c3ref/busy_timeout.html). Per the beta v24 doc mirror, the option's own "Added in" history reads **`v24.0.0, v22.16.0`** — i.e. it did not exist at all in earlier `node:sqlite` releases (the module itself shipped experimentally in v22.5.0, but without this constructor option).

`sqlite3_busy_timeout()`'s own reference page (sqlite.org) states it "sets a busy handler that sleeps for a specified amount of time when a table is locked. The handler will sleep multiple times until at least `ms` milliseconds of sleeping have accumulated. After at least `ms` milliseconds of sleeping, the handler returns 0 which causes `sqlite3_step()` to return `SQLITE_BUSY`." Critically: "Calling this routine with an argument less than or equal to zero turns off all busy handlers." So `timeout: 0` (the `node:sqlite` default) does not mean "wait zero milliseconds then fail gracefully" — it means **no busy handler is installed at all**, and a lock conflict returns `SQLITE_BUSY` immediately on the first attempt, with no retry/sleep loop. This confirms the ticket's premise directly: the out-of-the-box `DatabaseSync` default is immediate-fail-on-contention, not "wait forever" or "wait a moment."

**2. Per-connection option vs. `PRAGMA busy_timeout`**

The `timeout` constructor option only takes effect at connection-open time, applied to that one `DatabaseSync` instance/connection — it is not process-wide or file-wide. `PRAGMA busy_timeout = N;` is the underlying SQL-level mechanism the option wraps, and it remains issuable directly, e.g. via `database.exec("PRAGMA busy_timeout = 5000")`, since `exec()` is documented as "a wrapper around `sqlite3_exec()`" and the same docs page uses `PRAGMA foreign_keys` as its own example of a pragma issued through the connection. Both routes end up calling the same underlying SQLite mechanism (`sqlite3_busy_timeout()`); the docs give no indication of a difference in effect between setting it at construction time vs. issuing the pragma afterward. Given that the constructor option now exists and is documented as of v24.0.0/v22.16.0, that is the option Node's own docs foreground; nothing in the docs states the pragma route is deprecated or discouraged, only that the constructor option is newer.

**3. WAL and what triggers `SQLITE_BUSY`**

SQLite's own WAL document (https://sqlite.org/wal.html) states the general WAL concurrency promise ("writers do not block readers and readers do not block writers... This is mostly true") but the accessible page content only enumerated three specific `SQLITE_BUSY`-under-WAL cases directly: (a) another connection holding an exclusive lock, (b) the brief exclusive lock taken during connection close/cleanup, (c) the exclusive lock held during crash recovery. Separately, and consistent with well-established SQLite documentation elsewhere: **WAL mode is "multiple readers, single writer"** — a second writer attempting `BEGIN IMMEDIATE` (or any write) while another connection holds the write lock must wait for that writer to commit or roll back; it does not get to proceed concurrently. `busy_timeout` is what governs how long that second writer's wait/retry loop runs before giving up with `SQLITE_BUSY`. I could not extract, from the fetched WAL page content, an explicit sentence stating that readers are *never* subject to `busy_timeout`/`SQLITE_BUSY` under WAL — the enumerated exceptions above (exclusive-lock cases) are themselves reader-independent, but they show that "readers never see SQLITE_BUSY under WAL" is not an absolute in SQLite's own account. A benchmark should therefore not assume readers are categorically exempt without checking which of the three exclusive-lock conditions can arise in its own write pattern.

**4. Version-specific caveats a benchmark author should know**

- **Blocking, not async.** Node's own docs state plainly, for `DatabaseSync`: "All APIs exposed by this class execute synchronously" (same statement for `StatementSync`). This means any time SQLite's busy-handler sleeps inside `sqlite3_busy_timeout()`'s retry loop, it blocks the calling Node.js thread's event loop entirely. This is a fact any contended-write benchmark harness must account for: a `timeout` > 0 does not yield the event loop while waiting — it stalls it. This has been confirmed stable in Node's current docs (currently serving v26.8.2) and there is no note that this behavior differs on v24.
- **Stability level.** As of Node v24.15.0, the `node:sqlite` module's own stability marker is "1.2 – Release Candidate" (no longer "Experimental," which it was through earlier v22 releases). This should be recorded as the currency baseline for anything cited from these docs.
- **The `timeout` option itself is new to the exact Node version in use.** It was added in v24.0.0 and backported to v22.16.0. Any project or benchmark harness targeting Node versions before those (e.g. early v22.x before .16) will not have this constructor option available and must use the `PRAGMA busy_timeout` form instead — the origin GitHub issue (nodejs/node#57597, opened 2025-03-23) that led to this option being added states the pre-existing problem plainly: "the node:sqlite module's DatabaseSync initializer uses a default busy_timeout value of 0, causing intermittent 'database is locked' errors," and that users had been manually issuing `PRAGMA busy_timeout = 1000;` as a workaround before the constructor option existed.
- **Bundled SQLite version.** Node v24.15.0 bundles SQLite **3.51.3** exactly (verified directly against `deps/sqlite/sqlite3.h` in the `nodejs/node` `v24.15.0` tag: `#define SQLITE_VERSION "3.51.3"`). SQLite's own changes.html lists, as the headline fix for the 3.51.3 release: "Fix the WAL-reset database corruption bug." That means the version bundled with the Node release in use already carries this fix — worth recording as a currency check, not as an outstanding risk, since some search results reference this bug as a reason to require "3.51.3 or newer." A benchmark run on Node v24.15.0 is on the fixed side of that line, but this is worth re-checking if the Node version in use changes, since `node:sqlite`'s bundled SQLite version moves independently of the wrapper API.
- **Transaction-upgrade `SQLITE_BUSY` is a separate failure mode from lock contention, and `busy_timeout` does not cover it.** This is a general SQLite behavior (not `node:sqlite`-specific, and not from an official SQLite doc page in this search — flagged as a secondary/explanatory source, not a primary one): a connection that opens a transaction implicitly as read-only (its first statement is a read) and later attempts to write must "upgrade" that transaction; SQLite can refuse this upgrade immediately, without invoking the busy handler at all, because honoring it could violate its serializability guarantee. If a benchmark harness opens transactions generically (`BEGIN` rather than `BEGIN IMMEDIATE`) and then writes, it can see immediate failures unrelated to whatever `timeout`/`busy_timeout` value is configured, and would misattribute them to lock-contention timing if it doesn't distinguish the two. I have not been able to confirm this specific mechanism against an SQLite primary-source page directly (the search only surfaced a third-party technical write-up describing it); it should be treated as a claim to verify against `sqlite3_step()`'s or `BEGIN`'s own documentation before relying on it, not as confirmed primary-source fact.

## What I could not establish

- Whether `PRAGMA busy_timeout = N` issued via `exec()` after construction produces byte-for-byte identical internal behavior to passing `timeout` in the constructor (both are documented as ending at the same underlying `sqlite3_busy_timeout()` call, but I found no doc text explicitly asserting equivalence rather than merely implying it via shared implementation).
- Whether SQLite's WAL documentation, in full, asserts categorically that readers are *never* subject to `SQLITE_BUSY`/`busy_timeout` waits — the fetched excerpt gave three exclusive-lock exceptions but I could not confirm the page contains an unconditional "readers are exempt" statement, versus this being the accessible tool's summary of a partial excerpt of a much longer document. This should be re-read in full at https://sqlite.org/wal.html before a benchmark's interpretation of "who can get SQLITE_BUSY" is finalized.
- Whether there is a Node.js-specific (as opposed to general-SQLite) issue tracker report describing `timeout`/busy-handling behavior differences specifically between v22, v23, and v24 `node:sqlite` releases beyond the addition of the constructor option itself. Search did not surface one; its absence is not proof there isn't one, only that it did not appear in the queries run.
- The precise wording of the Node v24.15.0-specific docs page as archived at that exact version (as opposed to the current v24 beta mirror and the current live docs page, now v26.8.2) — Node's docs site does not appear to keep an easily fetchable frozen mirror per patch release; the "Added in" version tags quoted above are the mechanism by which the current docs identify what changed at which release, and they were cross-checked against the beta mirror rather than a frozen v24.15.0 snapshot.
