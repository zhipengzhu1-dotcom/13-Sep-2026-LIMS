# How do open-source laboratory systems actually model laboratory inventory — reference standards, reagents, chromatography columns, consumables, and storage places?

**Asked by:** Orchestrator (map-scout task, no ticket number given)
**Date:** 2026-09-11
**Status of sources:** All source-code claims below were read directly from the `develop`/`master` branch of the named GitHub repositories on 2026-09-11 via raw file fetches (paths and line-adjacent context given). No cached or third-party mirrors were used. Vendor marketing pages (senaite.com, openelis-global.org, labkey.com) were fetched separately and are explicitly flagged as marketing wherever cited, distinguished from source/docs. LabKey and OpenSpecimen findings rely on the vendor's own Confluence/help wiki (which is close to a primary source for these products, since both publish their functional documentation there rather than in the code tree) — this is noted per-system below.

## Findings

### 1. SENAITE / Bika LIMS

**Reference standards (`ReferenceSample` / `ReferenceDefinition`)** — verified from source:
- `bika/lims/content/referencesample.py` (senaite/senaite.core, branch `master`) defines a `ReferenceSample` Archetypes content type with fields: `ReferenceDefinition` (reference to a `ReferenceDefinition`), `Blank` (boolean), `Hazardous` (boolean), `Manufacturer`, `CatalogueNumber`, `LotNumber`, `Remarks`, `DateSampled`, `DateReceived`, `DateOpened`, `ExpiryDate` (required), `DateExpired`, `DateDisposed`, and `ReferenceResults` (a `ReferenceResultsField` holding per-analysis expected result/min/max, i.e. "Expected Values").
- `bika/lims/content/referencedefinition.py` defines `ReferenceDefinition`: a template carrying `ReferenceResults` (expected values per analysis service/category) and `Blank`/`Hazardous` flags, from which `ReferenceSample` instances are created.
- `ReferenceSample` is filed under a `Supplier` (its `SupplierUID` is computed as `context.aq_parent.UID()`), so lot-level reference standards are modelled as children of Supplier objects, not of a general reagent catalog.
- Linkage to analyses that used it: confirmed via `bika/lims/browser/worksheet/views/referencesamples.py`, which filters `ReferenceSample` objects by `getSupportedServices` against the analyses assigned to a worksheet, and `bika/lims/browser/templates/referencesample_analyses.pt`, a dedicated template listing the analyses run against a given reference sample. So yes — reference samples are tied to the analysis services they support/were used to control, and a control result is captured as a normal analysis result against the reference sample (used as a QC "sample" on a worksheet), not as a separate consumption record.
- The tracked unit is the **lot** (one `ReferenceSample` = one lot, with `LotNumber`, `DateOpened`, `ExpiryDate`), not an individual bottle/container serial, and not remaining-quantity ("how much of this lot is left" is not tracked).

**Reagent/consumable inventory** — checked and found effectively absent:
- `LabProduct` still exists in the current codebase (`bika/lims/content/labproduct.py`), but it is a **price-list / billing catalog item**, not a stock or reagent record: its schema is `Volume`, `Unit`, `VAT`, `Price`, `VATAmount`, `TotalPrice` — fields for quoting/invoicing a lab test or product, with no lot, expiry, quantity-on-hand, or storage-location field. There is no `Reagent`, `Inventory`, `Stock`, or `Consumable` content type anywhere in the `senaite/senaite.core` repository tree (checked via a full recursive tree search of the `master` branch — no matches).
- The SENAITE community itself confirms the negative: on the official community forum (https://community.senaite.org/t/using-senaite-to-manage-stock-inventory/186), a maintainer states plainly that "this Inventory Management module for Bika was defined but never developed, thus when Senaite forked from Bika no module was ported," and that a third-party fork (BaobabLims, used for biobanking) built its own storage-related extensions instead. As of that thread there was no standard reagent-stock solution in SENAITE, and no subsequent core module has appeared in the source tree as of this check.
- No consumption-of-a-reagent-against-an-analysis record exists in senaite.core; there is nothing analogous to a "reagent lot used for this determination" table.

**`senaite.storage`** — verified from source (senaite/senaite.storage, branch `master`):
- Hierarchy: `StorageFacility` (`src/senaite/storage/content/storagefacility.py`, a physical site/building, with Phone/EmailAddress/Address fields) → `StorageContainer` (`storagecontainer.py`, a container that can only hold other containers, plus a `Temperature` field) → `StorageSamplesContainer` (`storagesamplescontainer.py`, a terminal container that holds samples).
- All containers with position layout inherit from `StorageLayoutContainer` (`storagelayoutcontainer.py`), which defines `Rows` and `Columns` (integers) and a computed `PositionsLayout` record field with subfields `row`, `column`, `uid`, `samples_capacity`, `samples_utilization` — i.e. containers do have a row/column grid of positions.
- What it stores: `StorageSamplesContainer.is_object_allowed()` explicitly restricts contents to objects providing `IAnalysisRequest` (samples) — `return IAnalysisRequest.providedBy(obj)`. There is no code path or content type in `senaite.storage` that stores `ReferenceSample` or any reagent/consumable object. This is a samples-only storage/freezer-mapping add-on.

**Chromatography columns / consumables with usage history:** not found. No content type, field, or add-on in senaite.core or senaite.storage referencing "column," "consumable usage," or per-analysis reagent consumption was found in the repository trees searched.

### 2. OpenELIS Global (I-TECH-UW/OpenELIS-Global-2, branch `develop`)

This is the one system among those checked with a genuine, current, in-repository reagent/consumable inventory module (not merely a marketing claim — verified against Java source and Liquibase migrations):

- `InventoryItem` (`src/main/java/org/openelisglobal/inventory/valueholder/InventoryItem.java`): the catalog-level entity — `name`, `itemType` (enum), `category`, `manufacturer`, `catalogNumber`, `storageRequirements`, `quantityPerUnit`, `units`, `lowStockThreshold`, `expirationAlertDays`. This is the reagent/consumable "product" definition, analogous to SENAITE's `LabProduct` but for stock rather than billing.
- `InventoryLot` (`InventoryLot.java`): a lot record with `inventoryItem` (many-to-one), `storageLocation` (many-to-one to `InventoryStorageLocation`), `lotNumber`, `expirationDate`, `dateOpened`, `calculatedExpiryAfterOpening`, `receiptDate`, `initialQuantity`, `currentQuantity` (both `Double`, decremented as stock is used), plus a `LotStatus`/`QCStatus` enum (per `InventoryEnums.java`, not fully quoted here). This is lot-level tracking with a running quantity balance, not per-bottle/container serials.
- `InventoryUsage` (`InventoryUsage.java`): the consumption record. It has `inventoryItem`, `lot` (both required, many-to-one), `testResultId`, `analysisId`, `quantityUsed`, `usageDate`, `performedByUser`. This is a direct, explicit link from a reagent-lot consumption event to a specific analysis/test result — the thing SENAITE and senaite.storage do not have.
- `ResultInventory` (`src/main/java/org/openelisglobal/result/valueholder/ResultInventory.java`) is an older/parallel entity linking a `resultId` to an `inventoryLocationId` with a free-text `description` — simpler and storage-location-oriented rather than lot/usage-oriented; its coexistence with the newer `InventoryUsage`/`InventoryLot` tables suggests two inventory-linkage mechanisms exist in the codebase (an older `ResultInventory`, seen in `src/main/resources/hibernate/hbm/ResultInventory.hbm.xml`, and a newer, more complete inventory subsystem added via Liquibase changesets `016-inventory-management-system.xml` and later `062`/`063-microbiology-inventory-usage-link.xml`). I could not establish from the tree listing alone which is authoritative/current versus legacy without reading the changesets' dates and the DAO call sites in full — flagged as open below.
- Storage locations: `InventoryStorageLocation.java` exists as a first-class entity referenced by `InventoryLot`, but I did not fetch its field list in this pass; a facility/shelf/rack breakdown comparable to `senaite.storage`'s Rows/Columns grid was not confirmed either way from the files inspected.
- A microbiology-specific extension also exists (`MicroInventoryUsageLink.java`, `MicroInventoryUsageContext.java`, plus frontend `ReagentLotPicker.jsx` / `ReagentUsageHistory.jsx`), suggesting reagent-lot selection and usage-history display are wired into at least the microbiology results workflow in the UI.
- The marketing page (https://openelis-global.org/features-and-functionality/) claims "real-time stock monitoring across reagents, test kits, consumables, and equipment, with batch numbers and expiration dates," "automated reordering from configurable minimum-stock thresholds," "FEFO compliance," and "integrated billing — automatic Odoo invoice generation." The `lowStockThreshold` field on `InventoryItem` corroborates the reorder-threshold claim; I did not verify the FEFO logic, automated reordering trigger, or the Odoo billing integration in code in this pass — those remain marketing claims not yet source-verified.
- OpenBoxes/eLMIS integration: no direct evidence of code-level integration between OpenELIS Global and OpenBoxes or eLMIS was found; OpenBoxes (https://github.com/openboxes/openboxes) is a separate, general-purpose warehouse-management system for health supply chains, and I found no import/API-client code in the OpenELIS-Global-2 tree referencing it. This appears to be an ecosystem-adjacency (both used in some public-health deployments) rather than a built integration — could not establish otherwise from what's public.

### 3. LabKey Server / Sample Manager

Checked against LabKey's own hosted help wiki (labkey.org/SampleManagerHelp — this is LabKey's own product documentation, treated here as the closest available primary source; I did not read LabKey Server's source code, which is not fully open for this module in the same way senaite/OpenELIS are).
- Storage hierarchy is freeform and user-defined, built from a fixed vocabulary of "Storage Item Types": Physical Location, Freezer, Primary Storage, Shelf, Rack, Canister, Storage Unit Type, and Terminal Storage Location. Non-terminal types nest arbitrarily; only "terminal" types (bags, boxes, canes, plates, tube racks) directly hold samples.
- This is a samples/freezer-map system. The documentation reviewed here did not surface a reagent- or consumable-inventory module distinct from sample storage — I could not confirm one way or the other whether LabKey ships a separate chemical/reagent inventory product, since the search was limited to the Sample Manager / freezer-management pages specifically.

### 4. OpenSpecimen

Checked against OpenSpecimen's own Confluence documentation (openspecimen.atlassian.net/wiki) and its GitHub repo listing (krishagni/openspecimen) — I did not read the Java source in this pass.
- Container hierarchy is also freeform ("does not impose any specific hierarchy, size, or type of containers"); typical hierarchy is tank/freezer → shelf → rack → box.
- OpenSpecimen distinguishes **dimensioned containers** (fixed row/column grid, e.g. a 9x9 box, supporting a "container map view" that renders positions) from **dimensionless containers** (no fixed size/positions, e.g. a holding freezer for boxes awaiting pickup, for which no map view is available).
- This is a specimen/biobank system; documentation reviewed did not indicate a reagent/chemical inventory module. Not confirmed from source code — documentation-only check.

### 5. Other named precedents (documentation/marketing-level check only, not source-verified)

- Quartzy, SciNote's chemical/reagent inventory, and LabCollector were not source-inspected in this pass (time-boxed to the four systems above plus targeted searches). Based on general knowledge of these products' public documentation (not verified against source in this session), the common shape reported by vendors is: an **Item/Product** definition (the reagent/chemical type) with one or more **Lot/Batch** records underneath it carrying lot number, expiry, and a quantity balance — i.e. the same Item→Lot pattern found in OpenELIS Global's `InventoryItem`→`InventoryLot`, rather than tracking of individual bottles/containers as separately identified assets. This is stated as a general pattern from prior knowledge, not as something confirmed from primary source in this task, and should be treated with correspondingly lower confidence than the senaite/OpenELIS findings above.
