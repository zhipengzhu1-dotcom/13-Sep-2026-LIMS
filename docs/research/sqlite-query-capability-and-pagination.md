## Findings

### 1. FTS5 availability, `loadExtension`, and stability of `node:sqlite`

- Local probe on this machine: `node --version` → **v24.15.0**. Running `db.exec('CREATE VIRTUAL TABLE t USING fts5(x)')` against `node:sqlite`'s `DatabaseSync` succeeded, and an FTS5 `MATCH` query returned the expected row. `sqlite_version()` reports the bundled SQLite as **3.51.3**. This confirms FTS5 is compiled into the SQLite that ships with Node 24.15.0. (Confidence: high — direct local verification.)
- The `nodejs/node` repository's `deps/sqlite/sqlite.gyp` (fetched from the `main` branch on github.com, 2026-09-11) currently defines `SQLITE_ENABLE_FTS5` along with `SQLITE_ENABLE_FTS3`, `SQLITE_ENABLE_FTS3_PARENTHESIS`, `SQLITE_ENABLE_RTREE`, `SQLITE_ENABLE_GEOPOLY`, `SQLITE_ENABLE_MATH_FUNCTIONS`, `SQLITE_ENABLE_PERCENTILE`, `SQLITE_ENABLE_COLUMN_METADATA`, `SQLITE_ENABLE_DBSTAT_VTAB`, `SQLITE_ENABLE_PREUPDATE_HOOK`, `SQLITE_ENABLE_RBU`, `SQLITE_ENABLE_SESSION`, and `SQLITE_DEFAULT_MEMSTATUS=0`. (Source: `deps/sqlite/sqlite.gyp` on github.com/nodejs/node, main branch, as fetched today. Confidence: high, but note this is the *current* main branch, not necessarily identical to what shipped in every historical Node release — see version note below.)
- FTS5 (and the other flags above) were added via **nodejs/node PR #57621** ("sqlite: enable common flags"), which per its GitHub PR page merged 2025-04-04 and landed in **Node.js 22.16.0** (LTS, released 2025-05-21). Node 22.16.0 is the first version where FTS5 support in `node:sqlite` is documented to be reliably present; earlier Node 22.x builds did not have it. (Source: github.com/nodejs/node PR #57621, as summarized via automated fetch; I could not independently re-render the full PR diff/timeline beyond the summary returned. Confidence: medium-high — the PR number, its stated purpose, and the target version are consistent with the compile flags actually observed on Node 24.15.0, but I did not manually diff the exact pre/post `sqlite.gyp` content of that PR.)
- Local probe also confirmed, via `sqlite_compileoption_used()`, that on this Node 24.15.0 build: `ENABLE_FTS5=1`, `ENABLE_FTS3=1`, `ENABLE_MATH_FUNCTIONS=1`, `ENABLE_RTREE=1`, `ENABLE_STAT4=0`, `ENABLE_ICU=0`, `ENABLE_LOAD_EXTENSION=0`, `OMIT_LOAD_EXTENSION=0`. `ENABLE_JSON1` also reported `0` — this is expected and does **not** mean JSON is absent (see Q2).
- `DatabaseSync` exposes both `loadExtension(path[, entryPoint])` and `enableLoadExtension(allow)` as documented at nodejs.org/api/sqlite.html. Locally, with a `DatabaseSync` constructed without `{ allowExtension: true }`, calling `enableLoadExtension(true)` threw `"Cannot enable extension loading because it was disabled at database creation."`, and calling `loadExtension(...)` threw `"extension loading is not allowed"`. The Node docs (fetched today) state the constructor option is `allowExtension`, and that if `allowExtension` is `false` (the default) at construction time, extension loading cannot be enabled later — this matches what was observed locally. (Confidence: high — matches both live docs and live behavior.)
- Stability: the Node.js docs fetched today describe `node:sqlite` as Stability index **1.2 – Release candidate**, as of the Node version the fetch tool reported (v25.7.0 docs). This is **not** "Stable" (2.x) and not fully "Experimental" (1.0/1.1) either — it sits at the release-candidate rung of the experimental scale. The installed local Node is v24.15.0; I did not independently confirm the exact stability index text as shown specifically on the v24.x docs page (the fetch above pulled whatever the nodejs.org docs site currently serves, which may reflect a later Node line). (Confidence: medium — stability label confirmed for the docs as served today; not confirmed to be pinned to v24 specifically.)

### 2. Other SQLite compile-time features bearing on search/sort

- **Math functions**: `SQLITE_ENABLE_MATH_FUNCTIONS` is on (confirmed both via `sqlite.gyp` and local `sqlite_compileoption_used()`, and functionally via `sqrt(4)` returning `2`).
- **JSON**: `sqlite_compileoption_used('ENABLE_JSON1')` returns `0` on this build, but `json_extract(...)` works correctly. Per sqlite.org's JSON functions documentation (fetched today), **JSON functions have been built into SQLite core by default since version 3.38.0 (2022-02-22)**, and are now opt-*out* via `SQLITE_OMIT_JSON` rather than opt-in via `SQLITE_ENABLE_JSON1`. Node's bundled SQLite is 3.51.3, well past that threshold, so `ENABLE_JSON1` being unset is irrelevant — JSON1 functionality is present as a core feature, confirmed functionally. (Confidence: high.)
- **R-Tree**: `SQLITE_ENABLE_RTREE` is on in `sqlite.gyp` and confirmed locally — `CREATE VIRTUAL TABLE rt USING rtree(id, minX, maxX)` succeeded.
- **STAT4** (extended query-planner statistics for skewed data): `sqlite_compileoption_used('ENABLE_STAT4')` returned `0` locally — **not enabled** in this Node build. This means the query planner relies on ordinary `sqlite_stat1`-style statistics, not the finer-grained value-histogram statistics STAT4 provides.
- **ICU / Unicode-aware collation and LIKE**: `sqlite_compileoption_used('ENABLE_ICU')` returned `0` — the ICU extension is **not** compiled in. Functional local tests confirm the practical consequence: `'İstanbul' = 'istanbul' COLLATE NOCASE` → false, `'café' = 'CAFÉ' COLLATE NOCASE` → false, and `'café' LIKE 'CAFÉ'` → false, while plain ASCII case-folding (`'hello' LIKE 'HELLO'`) → true. This matches SQLite's documented behavior that the built-in `NOCASE` collation and `LIKE` case-insensitivity fold only ASCII A–Z/a–z; without the ICU extension, non-ASCII case folding (accents, Turkish dotted/dotless I, etc.) is not performed. (Confidence: high — directly demonstrated.)
- **Load extension**: `SQLITE_ENABLE_LOAD_EXTENSION` reports `0` and `SQLITE_OMIT_LOAD_EXTENSION` also reports `0` in the compile-option probe; in practice `loadExtension`/`enableLoadExtension` are present as JS-level API on `DatabaseSync` but gated entirely by the `allowExtension` constructor flag, as shown in Q1.

### 3. Keyset ("seek") pagination vs `LIMIT`/`OFFSET`

- SQLite's own `lang_select.html` documentation (section "5. The LIMIT clause", fetched today) states the semantics: "the first M rows are omitted from the result set returned by the SELECT statement and the next N rows are returned... Or, if the SELECT would return less than M+N rows if it did not have a LIMIT clause, then the first M rows are skipped and the remaining rows (if any) are returned." This defines the *behavior* of OFFSET but does not itself describe the execution-cost mechanism.
- SQLite's own optimizer documentation (`optoverview.html`, fetched today) does not describe any special-case optimization that lets the query planner "jump" an index B-tree directly to the Mth matching row for an arbitrary OFFSET; the documented optimizations in that page cover join ordering, MIN/MAX single-index lookups, and subquery co-routines, but no OFFSET-skip optimization is described. The well-established engineering conclusion — that with `ORDER BY` + `LIMIT`/`OFFSET`, SQLite (like most SQL engines) must walk and discard the first M rows of the ordered result before it can return the next N — is not contradicted by anything in SQLite's own docs, but is not stated in SQLite's own docs in so many words either. For the explicit statement of this cost characteristic I rely on a secondary source (below), which is well-established in the SQL community and consistent with SQLite's documented general execution model (index scans in sorted order, sequential row delivery).
- **Secondary but widely-cited primary write-up**: Markus Winand, "We Have a Problem with Offset" / "No Offset" (use-the-index-luke.com, article dated 2014-08-06, updated 2023-09-08, fetched today). It states that per relational theory/SQL-standard semantics, "the rows in the derived table are first sorted... and then limited by dropping the number of rows specified in the OFFSET clause," meaning the database must fetch and discard all skipped rows — cost grows with the offset regardless of indexing. It also flags a correctness issue: if rows are inserted/deleted between paged requests, offset-based paging can skip or duplicate rows for the user.
- Keyset (seek) pagination formulation, per the same source: rather than counting rows to skip, filter directly on the last-seen value of the sort key, e.g. `WHERE id < ?last_seen_id ORDER BY id DESC LIMIT N`. Requirements stated: the sort key must produce a **total, deterministic order** (i.e., unique per row, or made unique by appending a tie-breaking column, typically a primary key) so that "the next page" is well-defined; for a compound `ORDER BY (colA, colB)`, the keyset predicate must be expressed as a row-wise/tuple comparison (`(colA, colB) > (?lastA, ?lastB)`, or the logically equivalent OR-expansion `colA > ?lastA OR (colA = ?lastA AND colB > ?lastB)`) so that ties on the leading column are broken correctly by the next column. This composes with an index that matches the same column order as the `ORDER BY`, which lets SQLite satisfy the query via an ordered index scan (consistent with SQLite's own documented behavior in `optoverview.html` that the planner prefers index orders that avoid a separate sort step).

### 4. Total row count for a filtered list

- SQLite's own docs do not have a page dedicated to "cost of COUNT(*)"; `optoverview.html` (fetched today) contains no discussion of COUNT-specific optimization — the only aggregate-related optimization documented on that page is MIN/MAX single-index-lookup, which does **not** apply to COUNT.
- The mechanical consequence, consistent with SQLite's general documented execution model (no covering "count" metadata is maintained per index or table beyond what a query can derive from a scan): `COUNT(*)` over a filtered predicate requires the planner to actually scan and evaluate the filter against every row that could match — an index on the filtered column(s) helps insofar as it narrows or orders the scan (turns a full table scan into a range scan over the index), and if the count query needs no columns beyond what's in the index, the index can be used as a **covering** index for that count (avoiding the second table-row lookup described in Q5), but there is no shortcut below "touch every qualifying row." I did not find a written SQLite-authored statement enumerating this explicitly for COUNT; this is an inference from the documented covering-index mechanism (`optoverview.html`, section on covering indexes) and the absence of any COUNT-specific fast path in the same document. (Confidence: medium — mechanism is directly documented for covering indexes generally; its specific application to COUNT(*) is my inference, not a directly quoted SQLite statement about COUNT.)
- Established alternatives to a full accurate filtered count, as commonly documented across database engineering practice (not SQLite-specific, and not sourced to a single primary document): (a) fetch N+1 rows and use the presence of the extra row to signal "more results exist" without computing a total; (b) approximate counts (e.g., via `sqlite_stat1`/planner estimates, which are inherently imprecise); (c) omit a total count entirely and expose only forward/backward paging affordances. I present these as well-known patterns; I could not find a primary SQLite document that itself recommends or documents these as alternatives — they are general SQL engineering practice.

### 5. Partial and covering indexes

- **Partial indexes** — sqlite.org's `partialindex.html` (fetched today) documents two precise usability rules:
  1. If the index's `WHERE` clause is a disjunction (OR) of terms, the partial index can be used by a query whose `WHERE` clause is an AND-connected set of terms **if and only if at least one query term matches, verbatim, one of the index's WHERE terms** (e.g., index `WHERE a=5 OR b=6` can be used by query `WHERE b=6 AND a=7`, because `b=6` appears exactly in both). Matching is syntactic/exact — `b=6` does not match `b=3+3` or `b BETWEEN 6 AND 6` even though they're logically equivalent.
  2. If an index WHERE term is of the form `z IS NOT NULL`, it matches **any** comparison operator on `z` in the query (`=`, `<`, `>`, `<=`, `>=`, `<>`, `IN`, `LIKE`, `GLOB`), because any such comparison implies `z IS NOT NULL`.
  - Net effect: for the planner to use a partial index, the query's own WHERE clause must independently establish/imply the same restriction the partial index was built with — SQLite does not perform general implication reasoning beyond these two documented rules.
- **Covering indexes** — sqlite.org's `optoverview.html` (fetched today) documents the mechanism directly: an ordinary indexed lookup requires two binary searches — one on the index B-tree, one on the underlying table B-tree via the rowid recovered from the index. "If, however, all columns that were to be fetched from the table are already available in the index itself, SQLite will use the values contained in the index and will never look up the original table row... When an index contains all of the data needed for a query and when the original table never needs to be consulted, we call that index a 'covering index.'" This is stated to roughly halve the per-row cost for such queries ("can make many queries run twice as fast").

### 6. Sizing / latency figures for indexed range scans at 10^4–10^6 rows

- I could not find a primary sqlite.org document that publishes specific latency numbers (e.g., milliseconds per query) for indexed range scans at these row counts. sqlite.org's documentation focuses on algorithmic behavior (B-tree lookup costs, O(log N) index descent) rather than published wall-clock benchmark tables for arbitrary hardware.
- sqlite.org does publish general architectural claims (e.g., on `https://www.sqlite.org/whentouse.html` and `https://www.sqlite.org/np1queryprob.html`, not separately re-fetched in this session with full text) about SQLite performing well into the range of large single-file databases, but these are qualitative, not numeric latency figures for the specific 10^4–10^6-row range asked about.
- Any numeric millisecond-level figures I have seen referenced in the broader ecosystem for this row-count range come from third-party blog posts and benchmark repositories, not from sqlite.org itself. I am explicitly **not** citing any of those here as fact, per the instruction to prefer primary sources and mark absent authority as absent. **This sub-question is therefore marked low-confidence / not established from primary sources**: the only defensible primary-source claim is the qualitative one — that an indexed range scan's cost scales with the size of the range matched (via B-tree traversal, documented generally in sqlite.org's B-tree/index documentation) rather than with total table size, not a specific number of milliseconds at 10^4 vs 10^6 rows.
