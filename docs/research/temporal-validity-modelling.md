## Findings

### 1. Valid time vs transaction time vs bitemporal — vocabulary

- **Valid time** is the time period during which a fact is true in the modelled reality, independent of when it was recorded. **Transaction time** is the time period during which a fact was/is present in the database as the currently-recorded state (from insertion until superseded or logically deleted). A table tracking only the former is a *valid-time state table*; only the latter, a *transaction-time state table*; both together, a *bitemporal table*. This terminology originates with Richard T. Snodgrass and is carried into the SQL:2011 standard's temporal vocabulary (Snodgrass, "Temporal Databases," https://www2.cs.arizona.edu/~rts/pubs/EDC.pdf — this is Snodgrass's own paper, a primary source for the terminology, though it predates SQL:2011).
- These are not the same question. **Valid time answers "was it true then"** — reagent lot X's real-world expiry window. **Transaction time answers "what did we believe/record then"** — what the database held as of a given moment, including since-corrected mistakes. A bitemporal table lets you ask both simultaneously (e.g., "what did we believe on 14 March about whether the lot was valid on 1 March", useful when a record is corrected after the fact). SQL:2011's system-versioned tables implement transaction time; its application-time period tables implement valid time (see §2).
- I did not locate an authoritative one-line restatement of this valid-time/transaction-time split inside the SQL:2011 standard text itself (paywalled, not accessed directly); the definitions above are Snodgrass's, and Snodgrass is the acknowledged source the standard's temporal vocabulary derives from.

### 2. SQL:2011 temporal table features, and what SQLite supports

- SQL:2011 (ISO/IEC 9075:2011) defines two related but distinct temporal table mechanisms: **system-versioned tables**, which automatically retain every prior row version keyed by transaction time, enabling `AS OF` style history queries; and **application-time period tables**, which let application code declare a named period (e.g., start/end columns) with automatic period-splitting on UPDATE/DELETE, closed-open semantics, and constraint enforcement. Combining both yields a bitemporal table. (Secondary summary of the standard's content, not the ISO text itself — see currency note above.)
- **SQLite has no native support for either feature.** I checked the official SQLite SQL syntax documentation (https://sqlite.org/lang.html, fetched 2026-09-11) for any of: `PERIOD FOR`, `SYSTEM_TIME`, `FOR SYSTEM_TIME AS OF`, temporal, or versioned-table syntax — none appear. SQLite's supported DDL/DML surface (as of the locally installed 3.43.2 and the current docs) has no system-versioning clause, no application-time period clause, and no `AS OF` query syntax. This is a straightforward absence, not an assumption: the feature is not mentioned anywhere in the syntax reference.
- Consequence stated plainly: **anything temporal in a SQLite-backed system must be hand-rolled** — there is no engine-level mechanism to fall back on for either valid-time or transaction-time tracking.

### 3. Common hand-rolled patterns and their trade-offs, as reported by their own sources

The literature on this (Snodgrass's temporal-database work; Martin Fowler's "Bitemporal History," https://martinfowler.com/articles/bitemporal-history.html, a practitioner-authoritative but secondary source cited here because no primary standard covers hand-rolled patterns by definition) describes several recurring shapes:

- **Validity-interval columns on the row (`validFrom`/`validTo`)**: A point-in-time query is `WHERE validFrom <= :asOf AND (validTo IS NULL OR validTo > :asOf)`. This requires either overwriting the row in place when it changes (which destroys transaction-time history — you lose "what we believed before the correction") or inserting a new row and closing out the old one's `validTo` (which preserves valid-time history but requires every write to be a two-step insert+update, and requires the application, not the engine, to guarantee no overlapping intervals for the same entity — SQLite has no exclusion-constraint equivalent to enforce that).
- **An effective-dated history table alongside a current table**: keeps "what is true now" fast and simple to query (no interval predicate needed) while a separate table accumulates prior versions. Every mutation must write to both tables consistently; a point-in-time query in the past must always hit the history table with the interval predicate above, while a query for "now" can skip it. The cost is duplicated write logic and a class of bugs where the two tables drift if a write path forgets to update both.
- **Append-only event log with state derived by replay**: every change is recorded as an immutable event with its own timestamp; current or historical state for any point in time is computed by folding all events up to that time. This gives an exact transaction-time record "for free" (the log itself) and can support valid time if the event carries a separate effective-date field distinct from when it was logged. The cost reported by these sources is query cost: reconstructing state at an arbitrary point requires scanning/aggregating potentially many events per entity, which is why systems using this pattern typically also maintain a materialised current-state table or periodic snapshot to avoid replaying from the beginning on every read.
- **Snapshot-the-fact-at-use-time (copying the value onto the consuming record)**: instead of a general temporal query, the value under question (e.g., "was the lot within expiry") is captured and stored on the record that consumed it at the moment it was used. This answers "was it true then" trivially and cheaply for that one specific relationship, at the cost of not being a general mechanism — it only answers the question for entities that explicitly captured it at the time, and cannot answer it retroactively for a relationship that did not think to record it.

### 4. Indexing point-in-time range queries in SQLite

- SQLite's own optimizer documentation (https://sqlite.org/optoverview.html, fetched 2026-09-11) states the general multi-column index rule: "The initial columns of the index must be used with the `=` or `IN` or `IS` operators. The right-most column that is used can employ inequalities." For a predicate of the shape `WHERE validFrom <= ? AND (validTo IS NULL OR validTo > ?)`, both constraints are inequalities on different columns with no leading equality column, so **only one of the two range predicates can be used by the index to narrow the b-tree scan; the other is applied as a post-filter (a row-level check) on each candidate row returned**, per the documentation's own description of how additional WHERE-clause terms are handled once the rightmost usable indexed column is reached.
- I did not find, in SQLite's own documentation, any dedicated discussion of two-column range/interval ("interval overlap") indexing of the kind some other engines support via range or GiST-style indexes; SQLite's b-tree index structure does not have an equivalent. This is a documented absence rather than an inferred one — the general index-usage rule above is the closest applicable statement, and no interval-specific indexing feature is mentioned in `optoverview.html` or `lang.html`.
- The `OR (validTo IS NULL OR validTo > ?)` shape adds a further complication: SQLite's index-usage rule for inequalities is stated in terms of a plain conjunctive `AND` chain; a NULL-check `OR`'d with an inequality on the same column can defeat use of that column as the range-narrowing column altogether, depending on how the expression is phrased, per the same "rightmost usable column" logic — but I did not find a source addressing that OR-with-NULL case specifically, and I am not asserting a specific query plan SQLite would choose without testing it against the actual query.

### 5. Open/closed interval and NULL conventions

- The temporal-database and SQL:2011 sources describe **half-open intervals** (`[validFrom, validTo)` — closed at the start, open at the end) as the standard convention, because they compose cleanly: the end of one period can equal the start of the next with no gap and no overlap, and a "still open" / "still current" state is naturally represented by a sentinel (a very large/max date, or NULL meaning "no end yet") rather than requiring an update on every unrelated row when nothing has ended. This closed-open (or "closed set-open set") semantic is explicitly named in descriptions of SQL:2011's application-time period tables.
- NULL for "still valid" (open-ended) is a common convention in hand-rolled schemas per the same secondary sources, with the trade-off that every point-in-time query predicate must special-case NULL (as shown in the `validTo IS NULL OR validTo > ?` example above), which is exactly the shape that section 4 shows resists straightforward indexing.

### 6. Prior art in laboratory software — SENAITE

Checked directly against `senaite/senaite.core` at commit `993f721e6d8494d94a4001cd3d73409504b67a49`.

- **Reference-standard / reagent expiry** (`src/bika/lims/content/referencesample.py:187` defines an `ExpiryDate` `DateTimeField`; `src/bika/lims/content/referencesample.py:300-317` defines `isValid()`). `isValid()` compares `DateTime()` — i.e. the current moment at call time — against `getExpiryDate()`, a separate `getDateExpired()` field, and a `getDateDisposed()` field, returning `False` if the object is past any of them. The method itself carries a `# TODO: Do We really need ExpiryDate + DateExpired? Any difference?` comment (`referencesample.py:309`), i.e. SENAITE's own source acknowledges ambiguity between two expiry-like fields on the same object. There is no method taking an arbitrary point-in-time argument; validity is only ever evaluated as of "now."
- **Instrument calibration validity** is modelled as a distinct content type, `InstrumentCertification`, with explicit `ValidFrom` and `ValidTo` `DateTimeField`s (`src/bika/lims/content/instrumentcertification.py`, fields defined ~lines 121-137). `isValid()` on that object (`instrumentcertification.py:259-267`) is `valid_from <= today <= valid_to` where `today = DateTime()` — again evaluated only against the current moment, not a supplied date. Each certification is created as a new, separate child object of the `Instrument` (via `objectValues('InstrumentCertification')`, `src/bika/lims/content/instrument.py:456-459`); superseding a certification means adding a new object, not overwriting the old one, so the certification history is retained as a set of sibling objects, each carrying its own `ValidFrom`/`ValidTo` — structurally an effective-dated history collection (pattern 3b above), but every query method on top of it (`getValidCertifications`, `isOutOfDate`, `getLatestValidCertification`, all in `src/bika/lims/content/instrument.py:456-596`) is hardcoded to "now" (`date.today()` or `DateTime()`), not parametrized by an arbitrary `asOf` date.
- **Analyst qualification**: I searched the `LabContact` content type (`src/bika/lims/content/labcontact.py`) and the whole repository for `Qualification`/`qualified` and found no matches. SENAITE's source, as checked, **does not model analyst qualification as a time-varying (or even current-state) entity at all** — there is no qualification field, object, or validity method associated with `LabContact` in this codebase.
- **Method effectivity**: checked `src/bika/lims/content/method.py` and `src/senaite/core/content/method.py` for date/effectivity/retirement fields; none found beyond a uniqueness validator on the title field. SENAITE's `Method` content type, as checked, carries no effective-dated or retirement-dated validity fields.
